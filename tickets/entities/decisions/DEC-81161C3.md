## Decision

A sync peer authenticates to the source with a **peer key**: a random bearer
credential that rela itself verifies at the request edge. A valid key stamps the
principal `peer:<name>`. It is an ordinary grantable principal whose reads go
through the source's normal ACL. `peer:` is a reserved namespace, like
`integration:`: no header, environment value or JWT subject can assert it.

- **Key**: `relapeer_` followed by 32 random bytes in base64url. `rela peer key
create <name>` generates one and prints it once.
- **Storage on the source**: only the SHA-256 digest, as
`peer_key.<name>: sha256:<hex>` in `.rela/secrets.yaml` (or the systemd
credential). The key itself is stored nowhere on the source. The server re-reads
the file at most every 10 seconds, so adding or removing a key needs no restart.
- **Storage on the peer**: the peer's `.rela/secrets.yaml`, an environment
variable or a file. Never a config file.
- **Transport**: `Authorization: Bearer relapeer_...`. The prefix tells it apart
from a JWT, so it works next to `--jwt-*` and next to `--principal-header`.
- **Edge**: a request that presents a peer key is identified by the key only.
A wrong or revoked key answers 401 and never falls through to the header or the
JWT. The stamped principal then goes through `access.Opener` like any other: the
member-of walk and one `acl.Request` per request. The `principal_property`
lookup never applies to a `peer:` name, so a user entity cannot take over a peer
(RR-299TVAV).
- **Read-only**: a peer key authenticates `GET` and `HEAD` on `/api/v1/` paths
with no `_` segment and no empty segment, `GET` on `/api/v1/_schema` and
`/api/v1/_openapi.json`, and `POST /api/v1/_reconcile`. Anything else answers
403 `peer_route_refused` (RR-J0MY0JC). Sync pulls; the receiving side writes
locally as `system:<peer>` (TKT-I8L1EQU).
- **Roles**: `acl.yaml` assigns roles to `peer:<name>`. Without an `acl.yaml`,
every peer key is refused. The principal type is `peer`, so a baseline with
`applies_to: [peer]` can cap every peer.
- **Admission**: the reconcile gate is keyed on the principal, so every peer
has its own token bucket and slots (RR-KT1PVVG).

## Options considered

| Option | Verdict |
| --- | --- |
| `system:<peer>` with the token store (the original ticket text) | Not possible. `system:` is refused on every request path, and `internal/tokenstore` holds outgoing OAuth tokens; it authenticates nothing incoming (issue #2119). Loosening the guard is not acceptable. |
| Route-minted identity like `system:webhook:<id>` | Not a precedent. A webhook is unauthenticated by design: the proxy in front authenticates the producer, and the route only picks the principal. A read path with that shape would let anyone who reaches the port read as the peer. |
| Verified JWT from the IdP (`--jwt-*`) | Works today for deployments with an IdP that issues ES256 machine tokens (client credentials) with the source's audience. Needs token refresh on the peer and an IdP on every source; a header-mode or local source has none. Kept as an alternative: a peer may still authenticate this way, as an ordinary user. |
| Proxy header (`--principal-header`) | Works today but is only as strong as the proxy, fails open, and gives the proxy the job of holding peer credentials. |
| Peer key verified by rela (chosen) | One mechanism in every identity mode. The source holds only a digest. Fails closed. Revocation is a file edit. |
