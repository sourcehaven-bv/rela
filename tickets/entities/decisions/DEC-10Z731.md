## Decision

The sqlite build searches with SQLite FTS5, in the project's own database,
instead of a bleve index on disk.

## Why

DEC-LFSYNY paired SQLite with bleve and named FTS5 search as not licensed by
that decision. A `.rela` document should be one file, and the bleve index is the
last thing that needs a folder beside it (see
docs/architecture/desktop-documents.md). The postgres build already searches
inside its database; this does the same for SQLite.

## Constraints

- Built-in tokenizers only: modernc SQLite has no API to register a custom
FTS5 tokenizer (DEC-LFSYNY trade-off 4). The index uses the `trigram`
tokenizer, which answers case-insensitive substring queries. That is the
postgres build's search semantics (`LIKE '%needle%'` over a trigram index),
so the two database builds find the same entities. A needle shorter than
three characters cannot use the index and scans the table.
- The searcher implements `search.Backend` and passes the store conformance
search suites, so `search.Visible` and the ACL contract do not change.
- The index is derived data. It is rebuilt from the entities when it is
missing or its version changes, so it never needs a migration of its own.
