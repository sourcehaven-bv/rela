id: 'BUG-EB2BGR'
type: 'bug'
title: 'Screenshot capture has no retry, so a single cold-start timeout fails the whole docs build'
description: 'internal/docscapture had no retry around a capture: one transient failure failed the screenshot{} island, and with it the E2E job. Two distinct symptoms, one cause. (1) `manual:479: lua: context deadline exceeded` — the 30s perCaptureTimeout expiring on the FIRST capture. (2) `manual:478: resolve: screenshot(list ""): could not dial "ws://127.0.0.1:35025/devtools/browser/...": context deadline exceeded` — Chrome failing to start. Both landed on the first screenshot{} of a 16-screenshot manual and none on the other fifteen, which is the signature of cold start rather than of a figure that cannot be taken: the docs build runs on the same runner as the full Playwright suite and immediately after it, so the first capture stands up a temp project, starts a server, launches Chrome and loads the SPA on a machine still under load. newBrowser also had no bound of its own — it inherited the docs build''s root context, which is a signal context with NO deadline, so the only limit was chromedp''s internal dial timeout, and the --no-sandbox fallback then paid that wait a second time. Measured across the last 60 CI runs: only 4 failed at all, but 2 of those 4 were this flake, making it the largest single cause of CI failure in the repo. One of the two dequeued a PR from the MERGE QUEUE (run 35181768822), so it blocked a merge rather than just a PR check.'
priority: 'high'
why1: 'A screenshot{} island ran its capture exactly once, so any transient failure failed the island and the build.'
why2: 'The transient failures are concentrated at cold start: the docs build shares a runner with the Playwright suite and runs straight after it, so the first capture pays project stand-up, server start, Chrome launch and the first SPA load at once, on a loaded machine.'
why3: 'newBrowser had no timeout of its own. It inherited a signal context with no deadline, so a slow launch was bounded only by chromedp''s internal dial timeout and the no-sandbox fallback repeated that wait.'
why4: 'The capture path had a timeout for every step but no policy for what to do when one expired. A timeout expresses how long to wait, not whether the wait was worth repeating, and only the second question distinguishes a slow runner from a broken figure.'
why5: 'The build treated every failure as deterministic. For an operation whose cost depends on a shared CI runner''s load that is false, and the consequence fell on unrelated PRs: a contributor who changed nothing about the docs saw a red build naming a manual they had not touched, so the signal was both unactionable and misattributed.'
prevention: 'Capture now retries up to captureAttempts (3) with a pause between attempts, and the browser is torn down between them so the retry relaunches rather than reusing a tab left mid-navigation. Retryability is a property of the error, not a string match: errPageLoadFailed (the renderability gate''s error state), errRegionTooTall (the height cap) and errUnknownRole (a bad as= role) are sentinels that fail on the FIRST attempt, so a genuinely broken figure fails as fast and with the same message as before. The classifier is a DENY list over an allow list on purpose — transient failures are open-ended, so an unrecognised error is retried and at worst costs two extra attempts. newBrowser now bounds each launch with launchTimeout (25s) and reports both the sandboxed and no-sandbox reasons via errors.Join. The launch bound is applied with a TIMER, not context.WithTimeout: the first chromedp.Run allocates the tab and chromedp binds the tab''s lifetime to that context, so a child context would cancel the tab on return and every later action would fail with ''context canceled'' — which is exactly what happened during this fix and is now pinned by TestCapture_RetriesAgainstRealBrowser. Mutation-tested rather than merely re-run: setting captureAttempts=1 fails the transient cases, bypassing the classifier fails the deterministic case, and removing the browser reset reproduces the context-canceled bug. Verified end to end by building the real worlds manual against postgres (16/16 screenshots, all executable assertions passing). Generalizable lesson: a timeout says how long to wait, not whether to retry; any operation whose latency depends on a shared runner''s load needs both, and the retry decision belongs in a typed error rather than in matching on message text.'
status: 'done'
