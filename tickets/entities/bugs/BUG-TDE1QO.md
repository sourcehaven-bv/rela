id: BUG-TDE1QO
type: bug
title: 'ZIP-container documents (.docx, .xlsx, .odt, .epub) rejected on upload: mimeCompatible does not tolerate a sniffed application/zip'
description: 'internal/attachment/mimecheck.go runs two independent checks on every upload and the second contradicts the first. http.DetectContentType sees the PK\x03\x04 header and reports application/zip, which passes the allowlist (application/zip is in DefaultSafeMIMETypes). The sniff-vs-extension check then asks mimeCompatible whether the type the extension claims (mime.TypeByExtension(".docx") = application/vnd.openxmlformats-officedocument.wordprocessingml.document) is acceptable for a sniffed application/zip, and gets false, so the upload is rejected with "file extension implies ... but content is application/zip". mimeCompatible tolerates exactly one generic sniff result, application/octet-stream; application/zip is the other generic result the sniffer produces and it is not tolerated. Every ZIP-container format is affected: .docx/.xlsx/.pptx, .odt/.ods/.odp, .epub. A plain .zip uploads fine because claim and sniff both say application/zip. PDFs and images are unaffected. The file''s own doc comment says office docs are expected to sniff generically and that the code should lean on the extension-mismatch check, but that check is what rejects them.'
priority: high
why1: mimeCompatible returns false for a claimed OOXML/OpenDocument/EPUB type against a sniffed application/zip, so every ZIP-container document upload fails the sniff-vs-extension mismatch check.
why2: mimeCompatible tolerates exactly one generic sniff result, application/octet-stream. application/zip is the sniffer's other generic result, and it was not in the tolerated set.
why3: 'The design treated ''generic sniff result'' as a synonym for application/octet-stream. The doc comment on DefaultSafeMIMETypes states the belief explicitly: it says office docs sniff as octet-stream and that the mismatch check will cover them. They do not; http.DetectContentType matches the PK\x03\x04 header first and reports application/zip.'
why4: application/zip was added to the allowlist so ZIP-based uploads would pass the allowlist check, but the mismatch check was not revisited at the same time. The two checks encode overlapping assumptions about what the sniffer returns, and nothing ties them together, so updating one left the other contradicting it.
why5: 'The MIME rules were built from reasoning about stdlib behaviour rather than from its observed output, and no test exercised a real container-format file end to end. A wrong assumption about a third-party function was therefore recorded in a comment and encoded in two places instead of being caught. Security review exposed a second instance of the same root cause one layer down: the mismatch check resolves its claim through mime.TypeByExtension, which reads the OS MIME database, so both the original rule and the first fix behaved differently on a developer laptop than on the minimal container image rela actually ships in. The systemic cause is that a security decision was allowed to depend on ambient host state that no test controlled.'
prevention: 'The rule is now decided entirely in rela''s own source: the container set is keyed by extension (zipContainerExtensions) and the executable/macro-enabled containers are rejected positively via deniedExtensions, so no security verdict passes through mime.TypeByExtension. This follows the idiom internal/dataentry/apps.go already established for the same hazard. The regression tests build real ZIP archives rather than asserting an assumed sniff result, and the whole suite is verified to produce identical verdicts on macOS (populated MIME database) and in golang:1.26-alpine (no /etc/mime.types) — that cross-host check is what caught .docm and .xlsm being accepted on a minimal image while rejected locally. Generalizable lesson: when a check''s outcome depends on ambient host state, either remove the dependency or test on a host where the state is absent.'
status: done
