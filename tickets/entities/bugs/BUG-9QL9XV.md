---
id: BUG-9QL9XV
type: bug
title: ACL-hidden properties leak through _views section field values, and render as editable-but-403 in inline edit
description: Properties hidden by ACL policy (`visible:` block) are correctly stripped from `properties`, `_fields`, `_transitions`, `_attachments` and `_title` on the entity endpoints, but NOT from the `_views` section payload. `SectionFieldData.Values` is built directly from `e.Properties[f.Property]` with no visibility filter. Two user-visible symptoms follow from this one root cause.
priority: high
effort: s
why1: The detail view and the inline edit form still show ACL-shielded properties, and saving an edit on one fails because an empty value is submitted.
why2: The `_views` payload carries the shielded value in `sections[].fields[].values` (and `rows[].cells[].values`), so the detail view renders it; the inline-edit path then mounts a control for a field whose `_fields` verdict was correctly stripped, and `isFieldWritable(undefined)` defaults to permissive, so it routes as writable. The mounted control has no value (form data IS stripped), so editing submits empty -> `properties_unset` -> 403.
why3: '`sections.go` builds `Values` straight from raw `e.Properties` with no filter, three lines below where `Props` and `FieldVerdicts` ARE filtered via `copyVisibleProperties`/`computeFieldAffordances`. The stripping was applied per-field-on-the-struct rather than at the serialization boundary the whole response passes through.'
why4: 'There is no single choke point that guarantees "no hidden value reaches the wire". Entity responses go through `entityserializer.forWire` (which strips), but `_views` sections bypass that serializer and hand-roll their own DTO, so each new read surface must independently remember to strip. Two prior review-responses (RR-ROF51F `_attachments` leak, RR-C3OJ33 create-lock leak) are the same class of miss on other surfaces, and BUG-R9EHKV is a fourth variant leaking via titles rather than property maps. A full survey found ~30 unstripped projection sites across 9 unrelated DTO types, versus 12 correct sites on 1 type. A DTO-level choke point is NOT achievable: verdicts require the live `*entity.Entity` (`when:` predicates evaluate against its own properties and relations), so any interception at the DTO layer has already lost the entity. `SectionColumnData` additionally carries no property name at all — the name lives positionally in `sec.Columns[i]` — so a post-hoc filter cannot identify which cell is which property.'
why5: |-
    Field-visibility is enforced as a per-surface convention rather than a type-level or test-level invariant. Hidden-ness is represented by ABSENCE of a key, which is indistinguishable from "unset" — so neither the compiler nor a reviewer can tell a stripped payload from an unstripped one, and no test asserts the surface-agnostic property "a hidden value's bytes appear nowhere in any response". The existing `TestFeature_UC10_PropertyRedaction` tests the RESOLVER (that policy computes the right verdict), not that any given response honors it, which is why it passed throughout.
    Note the client CANNOT compensate: `_fields` is deliberately sparse (affordances.go:718-720 — "sparse: default is writable"), so a normal visible writable field emits no verdict at all. `undefined` therefore conflates "visible and writable" (the common case) with "hidden, verdict stripped" (the bug). Making `isFieldWritable` fail closed would render every ordinary form field readonly. The same side-channel closure that makes shielding secure is what makes the client unable to fail closed — so the fix must be that the field never reaches the client, not that the client gets smarter.
prevention: 'Byte-level wire-boundary test: policy hides a property whose value is a distinctive sentinel; the test walks every REGISTERED ROUTE (not a hand-listed set) and asserts the sentinel appears nowhere in the raw response bytes. Route enumeration is what makes it cover future surfaces automatically — pair it with a registry check that fails on any route neither exercised nor explicitly exempted with a reason. Byte-level scanning sidesteps the incompatible-DTO problem entirely and covers BUG-R9EHKV''s title variant with the same assertion. Secondary: retarget the "funnel" to the BUILDER layer (`buildSectionEntityData`, the entry-source branch, `buildRow`, the groupBy loop) — all four already have `ctx` and `a.affordances` in scope; this covers views + side panel but not sync/mentions/analyze/settings/feeds, which each need their own fix.'
status: done
