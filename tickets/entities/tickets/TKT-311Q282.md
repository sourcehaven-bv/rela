## Description

Define how scheduled flow starts behave. Inspired by Waymark's scheduling rules.
Applies to the `on schedule` start trigger; consider adopting the same defaults
for `schedules.yaml`.

- **Pinning.** A schedule pins the flow definition version (content hash)
and its start arguments when it is registered or the config loads. A later
config change takes effect at the next load, never for a run already in
progress.
- **Overlap.** By default a start is skipped while the previous run of the
same schedule is still active (`overlap: skip | allow`).
- **Missed starts.** No catch-up for starts missed while rela was down,
except at most one immediate start on resume (`catch_up: none | one`).
- **Single firing.** With several server processes, exactly one fires each
start (row lock or lease).
- **Jitter.** Optional random jitter to spread start times.
- **Visibility.** `rela flow schedules` (and an API/MCP equivalent) lists
each schedule with its next start and last run.

Builds on the runtime ticket TKT-9IT3LN8; do it with or right after it.

## Acceptance

- Tests cover pinning across a config change, overlap skip, missed-start
behavior on resume, and two processes firing once.
