## Description

The CalDAV collection ctag is derived from `EntityTypeWatermark(cfg.EntityType)`
— scoped by entity TYPE, never by a collection's filter or the caller's ACL.

With graph-driven dynamic collections (`project_tasks--PRJ-1`,
`project_tasks--PRJ-2`), two collections visible to different principals share
one underlying watermark. A principal who may read only PRJ-1 sees their ctag
change whenever ANY `task` is mutated, including in a project they cannot see.

No content leaks. What leaks is a low-bandwidth "something changed somewhere in
this type" signal, between principals the rest of that PR isolates carefully
(uniform 404s, an ACL gate on every driver lookup).

GitHub issue #1370. Source: IB-review of rela#1359. Severity: low.

**Violated requirement**: CONTROL-5-15 (access control rules shall be
established and implemented).

## Decision: accept as documented residual risk

The issue offers two paths — narrow the watermark scope, or accept explicitly as
a documented residual risk. **Accept**, decided by the project owner.

Both alternatives are worse, and for reasons that belong in the code rather than
in a closed issue:

**Narrowing the scope is forbidden by the design it would change.** The godoc on
`store.TypeWatermark` already considered and rejected it:

> A deletion tombstone records just (kind, id, type) — the deleted row's
> properties and relations are gone — so a narrower scope cannot be
> reconstructed once the row is removed.
>
> Do not "optimize" this into a per-collection or per-principal scope without
> solving the tombstone problem first.

Verified against the implementation: `writeEntityTombstone` persists `(id,
type)` only. A per-driver watermark could not see deletions in its own scope, so
it would go BACKWARDS when the newest row is deleted — and a tag that moves
backwards makes a client that already saw the higher value stop polling.
Permanently stale, with no way to notice. That trades a weak confidentiality
signal for silent data loss, in the direction the design explicitly calls
unsafe: "a missed change strands a client forever."

**Making tombstones remember more has a data-protection cost.** The fix would
require persisting the driver relation on delete, so "PERSOON-123 belonged to
project X" would SURVIVE that person's deletion. A tombstone that currently
holds only an opaque id and a type would start holding a relational fact about a
deleted subject — which is a GDPR/AVG question, not merely a schema change.
Deletion is supposed to remove personal data; making the deletion record retain
more of it inverts that.

**Falling back to ETag hashing costs what the watermark exists to save.**
`collectionCTag` renders the whole collection to hash per-entry ETags — exactly
the work the tag lets clients SKIP. It is quadratic for graph-driven
collections: P projects means P renders per client per poll cycle. That is a
deliberate, unbounded performance regression bought for a marginal
confidentiality gain.

## What the signal actually is

One bit — "a task changed somewhere" — with no identity, no content, and no
timing precision beyond the poll interval. A principal already knows the
deployment has tasks. Any shared multi-tenant system leaks comparable timing
signals through caches and latency.

## Scope

IN: extend the `store.TypeWatermark` godoc and the CalDAV docs to state what the
type scope discloses across differently-scoped dynamic collections, and why the
two narrowing options were rejected.

The godoc already explains why type-wide over-triggering is FUNCTIONALLY safe
(spurious re-sync vs missed change). It does not address the CONFIDENTIALITY
question that arises once one type is exposed through multiple,
differently-authorized dynamic collections. That gap is why this review finding
had to be raised from outside instead of being answered by the code.

OUT: any change to watermark scope, tombstone contents, or ctag computation.

## Acceptance

A reader arriving at `TypeWatermark` — or at the next IB review — finds the
analysis rather than re-deriving the finding. Specifically, the doc must answer:
what does a shared ctag disclose, why is per-scope not available, and what would
have to change first.
