## Understanding

- [x] Problem/requirements clearly understood
- [x] Scope defined (what's in/out documented below)
- [x] Acceptance criteria documented with specific test scenarios

**Problem:** Every relation gets its own cards section on the detail page, which is heavy for a single-valued status, owner or initiative.

**Scope:**
- In: `fields: - relation: <name>` in a view `properties` section on the entry; a compact picker that re-points a single-valued relation in one PATCH and adds or removes on a multi-valued one; `style_from` badges.
- Out: showing single-valued relations this way in the default view without config; `order_by` on the field.

**Acceptance Criteria:**
1. A relation field shows the target titles and changes them in place. Test: InlineRelationValue.test.ts.
2. A single-valued relation re-points in one PATCH. Test: "re-points a single-valued relation with a full linkage".
3. A multi-valued relation adds and removes single edges. Test: "adds and removes single edges on a multi-valued relation".
4. Validation: one of property or relation; only in `source: entry` with `display: properties`; the relation must exist and start at the entry type; `widget:` is refused. Test: TestValidateSectionRelationFields, TestValidateConfig_ViewRelationField.

## Approach

- [x] Technical approach chosen and documented
- [x] Approach builds on existing patterns (not reinventing)
- [x] Alternatives considered (document why rejected)
- [x] Dependencies identified (packages, APIs, types)

**Technical Approach:** Add a relation variant to the section field config, validated in dataentryconfig. The views handler sends the readable targets and their style value per field. The SPA renders InlineRelationValue inside SectionEditForm.

**Alternatives:** Reusing the relation cards section in a compact mode was rejected because the field must sit among the properties.

**Dependencies:** TKT-65LVAK for the one-transaction re-point.

**Files to modify:** internal/dataentryconfig/{config,validate}.go, internal/dataentry/{sections,views_handler}.go, internal/apiwire/v1/responses.go, frontend InlineRelationValue.vue, SectionEditForm.vue, sectionEditFields.ts, EntityDetail.vue, Badge.vue, PropertyDisplay.vue, the demo.

## Security Considerations

- [x] Input validation approach defined (allowlist preferred over blocklist)

**Input Sources & Validation:** View config validated at load; picker writes go through the relations PATCH.

**Security-Sensitive Operations:** Targets the caller cannot read are dropped from the field (TestRelationField_DropsUnreadableTarget). The field is read-only when the relation verdict denies writes.
