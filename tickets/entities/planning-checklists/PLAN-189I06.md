## Understanding

- [x] Problem/requirements clearly understood
- [x] Scope defined (what's in/out documented below)
- [x] Acceptance criteria documented with specific test scenarios

**Scope:**

In scope:

- A `task_item_conversions:` key in `schema.yaml`, validated at load.
- An API that offers recipes per entity and creates the target entity plus
the relation in one write.
- A button (one recipe) or menu (several recipes) on GFM task items in the
Milkdown editor, in the edit form and in the entity detail body editor.
- A prefilled create form when the mapping leaves required fields empty.
- Docs in `docs/metamodel.md` and `docs/data-entry.md` and their
`docs-project` mirrors.

Out of scope:

- Syncing the checkbox with the target's status (possible later automation).
- Create forms, embedded inline-create forms and custom apps
(`<rela-editor>`).
- Nested lines and sub-items. `{{item.text}}` is the item's own line.
- CLI and MCP surfaces.

**Acceptance Criteria:**

1. A source type with no recipe shows no button on task items.
2. With one recipe, a task item with text shows a button. Clicking it creates
the target entity with the mapped fields and creates the relation in the
configured direction. With `item: link` (the default) the item text is replaced
with `` `ID` ``. With `item: remove ` the item is deleted and its nested
sub-items move up into its place. Autosave stores the body.
3. With several recipes, the button opens a menu listing their labels.
4. No button on: create forms, plain bullets, empty task items, items whose
text is only an entity reference, and custom apps.
5. When the mapping leaves required target fields empty, a dialog asks for
only those fields and submits them to the same atomic endpoint. Saving applies
the recipe's `item ` mode. Cancelling leaves the item unchanged and creates
nothing.
6. A recipe is offered only when the principal may create the target type
(at the recipe's face), create the relation, and update the source. A direct
POST without those rights returns 403. An unreadable source returns the uniform
404, also when it has the wrong type. The update-on-source check is a UX gate,
not a security boundary: create plus relation rights reach the same result by
hand.
7. Invalid config fails the schema load with a specific error: unknown type
or relation, relation ends that do not fit the direction, unknown or computed
target field, unknown `{{source.x}} ` property, unknown interpolation
namespace, faced target without `face: `, `face: ` on a faceless target,
`item: ` other than `link ` or `remove `.
8. A faced target type is created at the configured face.
9. The audit log records the entity create and the relation create, and the
target type's on-create automations and cascades run, as for a normal create.
10. Item text is stored literally: text containing `{{source.x}} `, `{{new.x}} `
or `{{today}} ` is never expanded, in commit or preflight.
11. A field mapped from `{{item.text}} ` is subject to the field write gate,
like a value the caller typed.

**Technical Approach:**

Config:

```yaml
task_item_conversions:
  ticket-subtask:
    from: ticket
    to: task
    label: Convert to task
    relation: {type: has-subtask, as: to}   # new entity is the relation's `to`
    face: draft                             # required iff `to` has faces
    item: link                              # link (default) | remove
    fields:
      title: "{{item.text}}"
      project: "{{source.project}}"
```

1. Metamodel (`internal/metamodel/taskitemconversions.go `):
   - `TaskItemConversionDef ` on `Metamodel.TaskItemConversions `.
   - Register the key in `validTopLevelKeys ` (`loader.go `), give it a
root-only error in `include.go ` (as `copies: ` has), add it to the configedit
lock list, and list it in `acl map ` if that command reports recipe rights.
   - Validation: name pattern; `from ` and `to ` declared (may be equal);
`label ` required; relation declared and its ends fit `as `; `fields `
non-empty; target keys declared, not computed, not `external_ref `; `face `
per `validateConversionTargetFace `; `item ` is `link ` or `remove ` (empty
means `link `).
   - Templates are parsed once at load into tokens. The namespace allowlist
is exactly `item.text ` and `source.<property of from> `. Anything else
(`today `, `now `, `user.* `, `new.* `, `entity.* `) is a load error.
   - Refactor `validateConversionFields ` / `validateSourceReferences ` to take
`(fields, fromType, ...) ` so conversions and task-item recipes share the
target-key checks. The token parser is new.
2. Entitymanager, shared create preparation (`manager.go `):
   - Extract `prepareEntityCreate ` from `CreateEntity `: create face check,
`OpCreate ` authorization, field write gate, file and `external_ref `
rejection, manual-id check. `CreateEntity ` calls it; so does the new path.
   - Extract the post-create tail of `CreateEntity ` (audit, alias
notification, automations, automation property write-back, cascade) into a
shared helper that runs after commit.
3. Entitymanager, `TaskItemConverter ` (`taskitemconversion.go `):
   - Separate type so `Manager ` stays within its method budget.
`NewTaskItemConverter(m, gate) ` returns an error on a nil manager or gate.
   - `TaskItemEdgeGate ` is a consumer-side interface, like `CopyEdgeGate `:
"may this principal create relation R with this candidate entity at this end".
The dataentry wiring supplies it from the same relation gate `POST .../relations
` uses (`relationSources `, `when: `). `Offers `, `Preview ` and `Convert `
all use it.
   - Input: recipe name, source id, source face, item text, `properties ` for
required fields the mapping leaves empty (any other key is refused).
   - Text rule, in the engine: trimmed, non-empty, at most 1,000 runes, no
C0 controls, DEL, U+2028 or U+2029. The target's own `max_length ` still
applies.
   - Order, before the Tx:
     1. `ctx = withStoreAttribution(ctx) `.
     2. Read the source through the field-gated reader. Unreadable or absent
gives the uniform 404, before any type or permission check.
     3. Check the recipe's `from ` matches the source type.
     4. `source_face ` is required when the source type has faces; it must
name a face the source has.
     5. Every `{{source.x}} ` the recipe uses must be readable, else 403.
     6. Build the candidate: source tokens expand against the gated source
values (typed copy when the template is exactly one token), then the item text
is inserted as a literal. It is never re-scanned.
     7. `prepareEntityCreate ` for the candidate at the recipe face. The
field write gate covers every field whose template uses `item.text ` plus the
caller `properties `.
     8. Relation: build it from known types. The tail is the source face
when `as: to ` and the relation is content-scoped, the recipe face when `as:
from ` and content-scoped, and the zero face when identity-scoped (scope
helpers decide). Authorize with `RelationCreateRequest `, apply the relation
template, run `ValidateRelation `, and ask the edge gate.
     9. Authorize update on the source at `source_face `. This is a UX gate,
not a security boundary.
   - In one `Store.Tx `:
     1. Re-read the source; if any mapped source field differs from step 2,
refuse with a retryable source-changed error.
     2. Mint the id on the view.
     3. Run unique, relation capacity and owning-edge checks on the view.
     4. Only then write the entity (`createCore ` bound to the view) and the
relation (order assignment, then create). All checks run before the first write
because fs and mem `Tx ` cannot roll back.
   - After commit: the shared post-create tail, then the relation audit.
   - `Preview ` runs steps 1 to 8 without writing and returns the required
fields still empty. It returns no mapped source values, only field names, so it
cannot become a read channel.
   - `Offers(source) ` probes the same checks with `withAffordanceProbe ` and
returns `allowed ` and `reason `. The commit checks again.
4. API (`internal/dataentry/taskitemconversions_handler.go `):
   - `POST /api/v1/_task_item_conversions/{name} ` and `/{name}/preflight `.
Body: `source_id `, `source_face `, `text `, `properties `.
   - Commit returns the created entity's id, type, face and title.
   - The handler depends on a consumer-side interface (`Definition `,
`Preview `, `Convert `). Wired in `wireTypeChanges ` over `FieldGated(em) `.
   - Errors mirror `writeConversionError `: 403, uniform 404, 409
`schema_changed ` and source-changed, 422 for text and validation. A unique
conflict passes the create core's 422 through unchanged.
   - Offers go in `EditState ` as `_task_item_conversions ` (`name `, `label `,
`to `, `item `, `allowed `, `reason `). They are computed only on the
single-entity read, never on list responses, so the collection-reads rule is not
touched. No plimsoll pin bump.
   - OpenAPI operation ids use the prefix `convertTaskItem `; golden files
updated.
5. Editor (`frontend/src/components/forms/milkdown/ `):
   - Offers live in a ProseMirror plugin state. The button is a widget
decoration on each task item whose paragraph has text that is not only an entity
reference; the decoration set is rebuilt when offers change, so offers arriving
after mount show up.
   - The button is `contentEditable=false `, `mousedown ` is prevented, and
`stopEvent ` claims every event whose target is the button (including `keydown
`).
   - The editor emits `taskItemConvert({pos, text}) ` and exposes
`applyTaskItemResult(pos, text, {ref} | 'remove') `. It does no API work.
   - `applyTaskItemResult ` re-finds the item: the node at `pos ` must still
be a task item with the same paragraph text; otherwise the one task item with
that text; if none or several, it changes nothing and the caller shows a notice
with the new id.
   - `link `: `replaceWithEntityRef ` gains an option to keep the mapped user
selection and skip the trailing space. `remove `: delete the item, lift its
nested sub-items into its place, remove an emptied list. Both are one
transaction and one undo step, followed by `flush() `.
6. Orchestration (`frontend/src/composables/useTaskItemConversions.ts `, new
menu and dialog components):
   - One offer converts directly; several open a menu placed with
floating-ui (`linkPanelPosition.ts `).
   - Flow: preflight; if required fields remain, a dialog shows only those
fields (the `ConversionModal ` pattern) and submits them as `properties `;
then commit; then `applyTaskItemResult `.
   - The item's button is disabled while its request runs.
   - Hosts: `DynamicForm.vue ` passes offers only in edit mode; `EntityBody `
/ `EntityDetail.vue ` pass them for the detail editor. Custom apps never load
the task-list plugin.

Alternatives rejected:

- Server rewrites the stored body: breaks with unsaved editor changes and
needs a markdown locator for the item.
- Two client calls (create, then relate), including via
`InlineCreateFormModal `: not atomic, loses the recipe face, needs a form id,
makes the mapping editable and skips the update-on-source check.
- Extending `conversions: `: that key changes the type of the same entity,
with relation remapping and drops; mixing the two muddles both.
- Config in `data-entry.yaml `: the recipe is a server-enforced write, like
`conversions: `, so it belongs in the schema.
- Reusing `automation.Interpolate ` for the item text: its passes would
expand tokens inside the text.

## Security Considerations

- [x] Input sources identified (user input, config, external APIs)
- [x] Input validation approach defined (allowlist preferred over blocklist)
- [x] Security-sensitive operations identified (file access, auth, crypto)
- [x] Error handling doesn't leak sensitive information

**Input Sources & Validation:**

- Recipe name: must name a declared recipe; otherwise 404. Config names are
not secret, so a plain 404 on the name is fine.
- `source_id ` / `source_face `: resolved through the visibility reader first;
unreadable or absent gives the uniform 404 before any type or permission check.
`source_face ` is required for a faced source type.
- `text `: validated in the engine (allowlist of printable characters: no C0
controls, DEL, U+2028, U+2029; at most 1,000 runes; non-empty after trim).
Inserted as a literal after token expansion and never re-scanned.
- `properties `: only for required fields the mapping leaves empty; anything
else is refused. Field write gate and normal validation apply.
- Config: templates parsed at load against an allowlist of namespaces
(`item.text `, `source.<prop> `); invalid recipes fail the load.

**Security-Sensitive Operations:**

- Entity create: `prepareEntityCreate `, the same checks as a normal create,
at the recipe face; ceiling applies.
- Relation create: `RelationCreateRequest ` authorization, relation template,
`ValidateRelation `, and the injected edge gate that `POST .../relations `
uses. Tail face derived from the relation scope, never by world rank.
- Reading `{{source.x}} `: field-gated; a hidden mapped property is refused
(403). Values are re-checked inside the Tx; a change gives a retryable error.
Preview returns field names only, never source values.
- Caller-authored values: `{{item.text}} ` fields and `properties ` go through
the field write gate.
- Update on the source: a UX gate, documented as such.
- Offers are advisory (`withAffordanceProbe `, no denial audit); the commit
authorizes again. Attribution through `withStoreAttribution `; audit after
commit through the shared recorders.

- AC5: composable test: preflight with required fields opens the dialog;

- AC6: handler tests per missing right (create, relation grant, edge gate
`when: `, update) for offers (`allowed: false `) and commit (403); hidden
source of the right and of the wrong type give the same body as an absent id.
- AC7: table-driven metamodel tests, one row per error, including a
disallowed namespace and the `include.go ` root-only error.
- AC8: entitymanager test with a faced target; faced source with
content-scoped and identity-scoped relations, both `as ` values.
- AC9: entitymanager test asserts both audit entries and that an on-create
automation of the target type ran.
- AC10: text containing `{{source.hidden}} `, `{{new.x}} ` and `{{today}} ` is
stored and previewed verbatim.
- AC11: a write-denied field mapped from `{{item.text}} ` gives 403.
- Atomicity: entitymanager tests on mem, fs, sqlite and postgres; a full
relation capacity bound and a unique conflict each leave no entity.
- TOCTOU: a mapped source value changed between check and Tx gives the
retryable error and writes nothing.

**Edge Cases:**

- `remove ` on the only item of a list: the list is removed.
- `remove ` on an item with nested sub-items: they take its place at its
level, keeping their checked state.
- Item text with formatting (`**bold** `): `textContent ` is plain text; the
title is plain text.
- Item edited or deleted while the request runs: re-find by text; if gone or
ambiguous, change nothing and show a notice with the new id.
- Double click: the button is disabled while the request runs.
- Unicode and long text: length counted in runes; over 1,000 gives 422.
- Unique conflict on the target: the create core's 422, naming no colliding
id.
- Schema reloaded between offer and commit: 409 `schema_changed `.
- Faced target reference is a bare id; a reader whose world lacks the face
sees an unresolved mention (documented).

**Negative Tests:**

- Unknown recipe or a recipe for another source type: 404.
- Empty, oversized or control-character text: 422.
- `properties ` for a mapped field or an unknown field: 422.
- Missing `source_face ` on a faced source: 422.
- Missing rights: 403; hidden source: 404; hidden mapped property: 403.

## Risk Assessment

- [x] Technical risks assessed with mitigations
- [x] Security risks assessed (see Security Considerations)
- [x] Effort estimated (xs/s/m/l/xl)

**Risks:**

- Extracting `prepareEntityCreate ` and the post-create tail touches the main
create path: keep `CreateEntity ` behaviour identical; the existing create
tests guard it.
- fs and mem `Tx ` cannot roll back: all checks before the first write; tests
on every store.
- Stale editor positions after the request: re-find and check the item
before changing it.
- Method and field budgets: separate `TaskItemConverter ` type; offers in
`EditState `.
- A conversion before the body save is not idempotent: a crash before
autosave and a retry create a second entity. Documented.

Effort: l.
