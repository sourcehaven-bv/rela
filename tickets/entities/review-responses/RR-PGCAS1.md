title: pgstore's CAS kept a duplicate UPDATE that develop's content-states work had already outgrown
finding: '[correctness] Found by CI on the opened PR, not by local checks — which is the part worth recording. UpdateEntityIf was written as its OWN transaction and UPDATE statement rather than reusing UpdateEntity''s, and while the branch sat unrebased develop changed the shared shape underneath it (TKT-DOFYR1 content-states, plus the origin-provenance columns). The CAS copy kept the old shape and drifted in three ways at once: (1) it selected `id, type, properties, content, updated_at` — 5 columns — into scanEntity, which since content-states scans 6, so EVERY conditional write against PostgreSQL failed with "number of field descriptions must equal number of destinations, got 5 and 6"; (2) it addressed the bare id rather than (id, face), so even once scanning, it would have compared the version of the DEFAULT face against a write to a different one — the same class of defect as RR-1GM1NB, one layer down; (3) it omitted the origin_* columns UpdateEntity now stamps unconditionally, so a conditional write would have left stale provenance on the row. Blast radius was not limited to CAS: the data-entry PATCH path routes through PatchEntity + ExpectedVersion on this branch, so on a postgres deployment EVERY entity PATCH returned 422. CI showed it as 5 E2E failures (all `PATCH /api/v1/features/FEAT-001 -> 422`) plus the whole pgstore CAS conformance suite red. It was invisible locally because the pgstore CAS tests are gated on RELA_TEST_DATABASE_URL, which the review checklist had already flagged as unverified.'
severity: critical
resolution: 'Fixed in 6b930a8b. UpdateEntity and UpdateEntityIf now share ONE core (updateEntityIf): the unconditional path is the same function with a zero UpdateCondition, so a single UPDATE statement serves both and cannot drift again — the same shape the other three backends already used, and the reason only pgstore was affected. The conditional branch reads the row FOR UPDATE by (id, face) with the full 6-column projection before comparing in Go. Verified against a real PostgreSQL 17: the full postgres-tagged suite passes (105s), including TestCrossProcess_ConditionalUpdateConflictsInsteadOfLosing and TestCrossProcess_ConcurrentAppendersAllLandAcrossHandles, which are the cross-PROCESS acceptance tests the earlier local run could not exercise at all. Non-postgres backends re-verified green, lint and plimsoll clean.'
status: addressed
