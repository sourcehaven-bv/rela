title: ZIP-container tolerance and .jar/.apk/.xpi rejection both depend on the host OS MIME database
finding: 'mimeForExt uses mime.TypeByExtension, which consults the OS MIME database. Go''s builtin table contains only .apk, .docx, .pdf, .pptx, .xlsx, .zip (verified against $GOROOT/src/mime/type.go). On a distroless/scratch/Alpine-without-mailcap container — the normal way to ship a Go server — .odt/.ods/.odp/.odg/.epub and .jar/.xpi all resolve to the empty string. Two consequences, in opposite directions. (1) The fix silently stops applying to OpenDocument and EPUB, so the bug returns on exactly the deployment the fix was written for. (2) The whole mismatch check is gated on `claimed != ""`, so a .jar or .xpi gets NO check at all and uploads successfully — the case TestMIME_ZipToleranceIsNotBlanket claims is blocked. The security posture inverts with the deploy image, and the test is green on a developer laptop for an environmental reason. Bounded by the fact that identical bytes already uploaded fine named .zip, and by Content-Disposition: attachment on download, so not critical — but the change documents and tests a rejection guarantee that a realistic deployment does not have.'
severity: significant
resolution: 'Fixed both directions. (1) The container set is now keyed by EXTENSION (zipContainerExtensions) rather than by the host-resolved MIME type, following the idiom internal/dataentry/apps.go already established for this exact problem (''deterministic regardless of the deploy box''s OS MIME registry''). (2) The executable and installer ZIP containers .jar/.war/.ear/.apk/.xpi/.crx/.appx/.msix/.ipa are added to deniedExtensions, so their rejection is a positive check that runs before any MIME lookup instead of depending on a claim that does not exist on a minimal image. Verified empirically in a golang:1.26-alpine container with NO /etc/mime.types: before the rework .docm/.xlsm were accepted there while rejected on macOS; now all 11 TestMIME_ tests pass identically on both. Also found and fixed during verification that .crx and .ipa resolved to an empty claim even on the fully-populated macOS host, so they were previously unchecked.'
status: addressed
