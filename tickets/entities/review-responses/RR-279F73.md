type: review-response
title: Property-referenced RRULE value not validated at render (malformed rules break clients)
finding: 'Config validation accepts rrule: <property> by checking only the property exists, so rrule: on (a date property) validates; at render, RRULE:2026-07-20 is emitted verbatim — a malformed rule that Apple/Google calendar clients reject, often failing the ENTIRE feed import, not just one event. The config validator can''t know the runtime value, so the render path must validate the resolved RRULE (parse via rrule-go) and skip/omit on failure, consistent with the tolerate-bad-data ''skip the event'' policy already applied to unparseable dates. (Overlaps C1''s fix if render-time rrule validation is chosen.)'
severity: significant
resolution: resolveRRule now validates the resolved rule (validRRule via rrule-go) for BOTH literal and property-referenced values, and drops an invalid rule rather than emitting it — so a property holding a non-rule (or a date) yields no RRULE instead of a malformed one that breaks the whole feed. Pinned by TestDeclarativeFeed_MalformedPropertyRRuleDropped (invalid dropped, valid kept).
status: addressed
