title: migrate both-files refusal is unreachable dead code; docs promise a safety property that does not exist
finding: 'renameLegacySchema returns early unless ctx.SchemaIsLegacy, but SchemaIsLegacy is only true when SchemaFileAt fell through to the legacy name — which by construction means schema.yaml does NOT exist. So the `fs.Stat(target)` both-files guard below it can never fire; it is unreachable. Confirmed: with both files present MigrateWithFS returns (nil error, renamed="") and leaves the legacy file in place. Three consequences: (1) the refusal branch is dead code no test can reach through MigrateWithFS; (2) docs/cli-reference.md documents behaviour that does not exist — ''If both files already exist, the rename is refused rather than overwriting schema.yaml''; there is no refusal, only silence; (3) LegacySchemaPending also returns false, so `rela migrate --check` reports ''No migrations needed'' and passes CI while an orphaned metamodel.yaml lingers unreported forever. The function''s doc comment also misattributes the rationale to os.Rename''s silent POSIX replace — a real hazard, but not the one this guard addresses, since the target is already guaranteed absent. Shipping a doc that claims a safety property the code lacks is the specific failure that costs trust when an operator with both files runs migrate and assumes they were protected.'
severity: critical
resolution: 'The reviewer was right that the guard was unreachable. Rather than move the same check somewhere it could fire, I chose the behaviour that fits what the state actually means: an orphaned metamodel.yaml beside a live schema.yaml is not a pending rename (there is nothing to rename it to), so refusing the whole migrate would block unrelated content migrations over a stale file. Added projectsetup.OrphanedLegacySchema + MigrateResult.OrphanedLegacySchema; `rela migrate` now prints ''Note: metamodel.yaml is being IGNORED because schema.yaml exists...'' and `migrate --check` reports it and exits 1 (verified: real exit=1). The operator''s file is reported, never deleted — that is not migrate''s call. renameLegacySchema''s doc now states plainly that the both-files case cannot reach it and why the rename is therefore never an overwrite. docs/cli-reference.md and the metamodel guide were corrected to describe the real behaviour instead of a refusal that never existed.'
status: addressed
