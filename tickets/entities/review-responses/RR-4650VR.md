type: review-response
title: file/attachment properties would be prefilled with a dangling reference
finding: Attachments are stored at attachments/<entityID>/<property>/<fileName> (internal/attachment/attachment.go:95) and the property value is just the filename. Duplicating a file-typed property therefore copies a filename whose bytes live under the SOURCE's id, so the copy renders an attachment that 404s on download. The ticket lists attachments as out of scope but also says the prefill carries 'all properties the caller can see', which includes file properties — so out-of-scope currently means 'silently broken' rather than 'excluded'.
severity: significant
resolution: Ticket now excludes file-typed properties from the prefill, with the attachment path rationale, plus AC19b asserting no dangling attachment reference.
status: addressed
---

## Resolution required

Make the exclusion explicit: `file`-typed properties are omitted from the
duplicate prefill, and add an AC asserting a duplicated entity has no dangling
attachment reference.

"Attachments out of scope" must mean excluded, not carried-and-broken.
