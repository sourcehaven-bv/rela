id: RR-82519A
type: review-response
title: 'icon: none on an action entry drew a document glyph in the collapsed sidebar — a button that fires a mutation, rendered identically to a link to a document'
finding: |-
    An `action:` entry fell through the kind switch without setting `item.Icon`, so for `action:` + `icon: none` the new `DerivedIcon` was `""`, which `omitempty` dropped. `NavIcon` then called `resolveIcon(null)` and got `DEFAULT_ICON` — FileText.

    So a collapsed sidebar showed a **document glyph** on a button that runs an action, sitting in a column of real `document:` links. There is no confirm dialog in `handleAction`; it just runs.

    Failure scenario: an author writes `label: "Archive Sprint", action: archive_sprint, icon: none` (reasonable — they do not want it drawing attention). The user collapses the sidebar, sees a row of identical document icons, clicks the wrong one, and archives the sprint.

    This is worse than the bug RR-85NWY3 was raised about. An invisible row is a discoverability problem; a document icon that fires a mutation is a wrong-action problem.

    And `NavIcon.test.ts` enshrined it: the test asserted only that an `svg` existed, which passes for the wrong glyph.
severity: significant
resolution: |-
    An action entry now derives its own glyph (`zap`, via `icondefs.DerivedNames.Action`). That removes the empty-fallback case entirely rather than special-casing it — every entry kind derives something now, so the "action is the one kind with no glyph" caveat disappears from three comments as well.

    Tests: `TestActionEntryNoneHasACollapsedFallback` asserts the fallback is non-empty, is a renderable name, and is specifically NOT `document` (the two must not be indistinguishable). The NavIcon test now pins WHICH glyph renders by its Lucide class rather than asserting an svg exists — that weak assertion is what let this through. The pre-existing `nav_icon_test.go` case asserting actions derive nothing was updated with the reason it changed.
status: addressed
