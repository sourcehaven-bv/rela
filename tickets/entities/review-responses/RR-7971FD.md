## Finding

`countingStore` embedded `comments.Store`:

```go
type countingStore struct {
	comments.Store
	lists int
	gets  int
}
```

Embedding means the struct satisfies the interface no matter what the interface
gains. Add a method, forget to implement it on the double, and the result is a
nil-pointer panic at call time rather than a build failure — the failure lands
far from the omission that caused it. Convenient today; a trap on the next
interface change, which this very ticket demonstrates is a thing that happens.

## Resolution

Replaced the embedded interface with a named `inner comments.Store` field, added
`var _ comments.Store = (*countingStore)(nil)`, and wrote explicit pass-throughs
for all seven methods. Adding an eighth now fails the build here, which is where
the problem would be.

The reviewer also flagged the plain-`int` counters as a race risk. Not adopted:
the test is not parallel, the counters are written by a single `Get` call and
read after it returns, and adding a mutex to a sequential test double would be
noise. The race detector is on in CI and has nothing to flag.
