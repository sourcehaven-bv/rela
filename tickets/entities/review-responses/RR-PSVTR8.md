title: joinErrors lost error identity above one problem; ChainFor's second result was documented as load-bearing but discarded
finding: Two small API-honesty defects. (1) worlds.joinErrors wrapped a single error with %w but flattened two or more via strings.Join(parts, "; "), so errors.Is/errors.As worked for one problem and stopped working for two. No consumer inspects these today, but the asymmetry is the kind that surprises later, and errors.Join is already used in-tree (internal/affordances/resolver.go:157). (2) metamodel.WorldDef.ChainFor returns (chain, ok) and its godoc said 'callers must not treat a nil chain as "select nothing" without consulting it' — but the sole production caller, compileWorld, does `rawChain, _ := def.ChainFor(typeName)` and discards it. Harmless today (resolveChain(nil) returns nil and rule 3 applies either way), but a PR-D author reading that doc would assume the distinction survives compilation; it does not.
severity: minor
resolution: 'Both fixed in 322aa4b6. (1) joinErrors now returns fmt.Errorf("worlds: %d problems: %w", len(errs), errors.Join(errs...)), preserving errors.Is/As at every arity; the comment records why. TestCompile_ReportsEveryProblem still passes since it asserts on substrings. (2) ChainFor''s godoc was rewritten to state what is actually true: the second result reports whether a NON-EMPTY chain applies, the two branches coincide today (empty chain and no chain both mean rule 3, take Otherwise) which is why the compiler discards it, the loader separately rejects an explicitly empty select:/override chain, and it is returned for a caller that must tell ''declared but empty'' from ''not declared''. Also added a comment at compileWorld''s fallback assignment noting that any non-`default` Otherwise compiles to exclusion deliberately — unreachable for a loaded schema since the loader rejects unrecognized values, and fail-closed if it ever became reachable. Found by code review.'
status: addressed
