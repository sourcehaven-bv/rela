title: rela init clobbers an existing legacy project (data loss)
finding: 'The plan says `rela init` should create schema.yaml, but does not address the already-initialized guard. internal/projectsetup/init.go:43-47 computes `metamodelPath := filepath.Join(targetDir, project.MetamodelFile)` and errors only if THAT path exists. If the constant is repointed to schema.yaml (or the code switched to SchemaFile) without widening the guard, running `rela init` in an existing legacy project — one containing metamodel.yaml — would find no schema.yaml, conclude the project is uninitialised, and proceed. ctx.Initialize() then recreates directories and fs.WriteFile writes a DEFAULT schema.yaml alongside the user''s real metamodel.yaml. Because discovery prefers schema.yaml, the project silently comes up on an empty default schema while the real one is ignored: every entity fails type resolution. This is user data loss triggered by a plausible command in a legacy project, and it is exactly the failure the plan''s own ''prefer schema.yaml'' rule makes silent rather than loud. Fix: the init guard must stat BOTH names and refuse if either exists, with a message distinguishing ''already initialized'' from ''legacy project — run rela migrate''. The same class of bug exists in the desktop new-project path at cmd/rela-desktop/main.go:423-424, which has no existence guard at all.'
severity: critical
resolution: Plan updated before implementation. The init guard now stats BOTH names and refuses on either, with distinct messages for 'already initialized' vs 'legacy project — run rela migrate'. Captured as approach step 9, acceptance criterion 7 (asserting refusal AND that no schema.yaml is written), a named edge case, a negative test for partial-initialisation cleanup, and the top row of the risk table. The identical unguarded write in the desktop new-project path (cmd/rela-desktop/main.go:423-424) is called out explicitly in the files-to-modify table.
status: addressed
