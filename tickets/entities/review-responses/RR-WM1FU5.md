title: Test helper duplication, missing subtests, decorative parameters and duplicated rationale prose
finding: Housekeeping from the code review, grouped. (a) newDefaultSafeApp was a copy-paste of newGlobalAttachmentsApp with two lines deleted — same config literal, parse, wiring, ACL and seed. (b) None of the new tests used t.Run subtests despite CLAUDE.md preferring table-driven tests with them; one loop had seventeen cases. (c) zipBytes/zipArchive took a `member` parameter that cannot affect any verdict, implying a sensitivity the helper's own comment documents as absent, and the two helpers were byte-identical under different names. (d) The OS-MIME-database rationale was restated in six places, which the duplication rule warns gets corrected in one and goes stale in five. (e) The deniedExtensions comment claimed the macro-enabled extensions are absent from Go's builtin table; they resolve fine on a populated host, and the real point is that a minimal image lacks them.
severity: nit
resolution: All five applied. (a) Both builders now call one newAttachmentApp(t, metaYAML); newGlobalAttachmentsApp adds only the command runner, newDefaultSafeApp is a one-line delegation. (b) Every new test is table-driven with t.Run subtests, so a failure names its case and `go test -run '.../\.crx'` works. (c) The member parameter is gone from both helpers, both are named zipBytes, and the comments state that the archive's contents cannot affect a verdict. (d) The rationale lives on zipContainerExtensions; the tests cite the reason rather than restating it, and TestMIME_ExecutableZipContainersDeniedByExtension points at the behavioural test instead of repeating why. (e) The macro-group comment now says a minimal image resolves them to no claim, which is the accurate statement. Also dropped a test that had become redundant once TestMIME_AllowsZipContainerDocuments started iterating zipContainerExtensions directly.
