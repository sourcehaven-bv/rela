finding: |-
    CENTRAL AUTH QUESTION — resolved recommendation: option (a) proxy-only trust, but with a required guardrail the plan omits. Verified against internal/dataentry/middleware_security.go and router.go:

    1. The endpoint must be added to `nonBrowserExemptPrefixes` (not a new bespoke exemption) so it reuses the existing, carefully-reasoned `isCSRFExempt` heuristic (Sec-Fetch-Site absent + no Cookie + no Origin/Referer). A background ICS poller (curl-like) sends none of those → exempt; a browser fetch() always sends Sec-Fetch-Site → NOT exempt (correctly still same-origin gated). This is exactly the sync-API precedent and is the right mechanism.

    2. THE GAP: rela's `defaultPrincipalResolver` stamps `Principal{User:"unknown"}` (router.go:242-248). Under `acl.NopACL` (the default when no acl.yaml exists), the read gate permits everything. So a feed endpoint that is CSRF-exempt AND has no proxy AND has no acl.yaml serves the ENTIRE graph to anyone who can reach the port — with no warning. The plan's 'proxy authenticates' assumption silently degrades to 'no auth at all' in the common local/no-ACL case.

    RECOMMENDATION: (a) proxy-trust as the model, PLUS a fail-loud guard: if the feed endpoint is reachable on a non-loopback bind with neither a principal-header configured nor an acl.yaml present, log a prominent startup/first-request WARNING (mirroring the existing bind-beyond-loopback warnings in cmd/rela-server/main.go) — or refuse to serve feeds — so the operator can't accidentally expose the graph. Loopback + unknown principal is acceptable for local PIM (option c) and needs no token. Do NOT rely on the proxy silently; make the unsafe configuration observable. Option (b) rela-side Basic is rejected as the default (rela has no credential store and the CLAUDE.md model is proxy-does-auth), but keep it as a documented escape hatch for no-proxy multi-user.
