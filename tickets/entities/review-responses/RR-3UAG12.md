title: Retained aliases grow unbounded, and every write rewrites the whole table
finding: Now that aliases are retained as tombstones (RR-B4RZRA, and the EntityDeleted no-op), the table is append-mostly and nothing prunes it. persistLocked rewrites, sorts and MarshalIndents the ENTIRE table on every single write - O(n) alloc + O(n log n) sort + a full fsync per to-do edit. At a few thousand tombstones on a busy list, every check-off pays for the whole history.
severity: significant
resolution: 'DEFERRED with a follow-up recorded on TKT-MF1CWZ. Not a correctness bug and not a regression: the whole-table rewrite predates this branch and was a deliberate trade documented on persistLocked (a single atomic write keeps the table internally consistent, where per-key files could half-apply a rename across a crash). What changed is the growth rate, since deleted entries now stay. Acceptable at PIM scale - the fsstore backend is a single user''s project - but a multi-user postgres deployment needs pruning. The natural fix is a deletion timestamp on the alias plus a prune horizon, or reconciliation against the pgstore deletions table; both want the postgres-backed alias variant already noted on TKT-WAA092 rather than a bolt-on here.'
reason: Deferred to a follow-up recorded on TKT-WAA092 and TKT-MF1CWZ; not a correctness bug and not a regression. The whole-table rewrite predates this branch and is a deliberate documented trade on persistLocked - a single atomic write keeps the table internally consistent, where per-key files could half-apply a rename across a crash. What this branch changed is the growth RATE, since aliases are now retained as deletion tombstones. That is acceptable at the scale the fsstore backend targets (one user's project, where the table holds one entry per synced to-do plus deleted ones). The fix belongs with the postgres-backed alias variant already scoped on TKT-WAA092 - a deletion timestamp plus a prune horizon, or reconciliation against the pgstore deletions table - rather than as a bolt-on to the in-memory JSON table, because a multi-writer deployment needs that variant anyway.
status: deferred
