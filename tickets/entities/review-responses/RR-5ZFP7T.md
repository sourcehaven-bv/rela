title: Documented systemd unit grants @mount wholesale, broader than bubblewrap needs
finding: 'The guide''s systemd unit is copied verbatim by operators, so it is a security artifact. Two of the three relaxations are correctly minimal: RestrictNamespaces=user mnt pid net ipc uts cgroup is exactly the set --unshare-all expands to (sandbox_linux.go:94-96), and AF_NETLINK is genuinely required (bwrap brings up loopback in its new netns; the RTM_NEWADDR signature in usernsFailure corroborates it). But SystemCallFilter=@system-service @mount ... grants the whole systemd-maintained @mount set — mount, umount2, pivot_root, chroot, move_mount, open_tree, fsopen, fsconfig, fsmount and more — where bwrap needs only mount, umount2 and pivot_root. The doc''s own caveat that @mount contents vary across systemd releases is an argument AGAINST using the set: the grant silently widens on a systemd upgrade. Not attacker-reachable (host unit grant-surface, exploitable only after a separate RCE in rela-server); it widens post-exploitation options rather than creating an entry point. Fix: SystemCallFilter=@system-service mount umount2 pivot_root unshare setns clone clone3, keeping the version caveat — with an explicit list it then protects against a narrowing upgrade, which fails closed.'
severity: minor
status: addressed
resolution: 'Replaced @mount with the three syscalls bubblewrap actually issues: SystemCallFilter=@system-service mount umount2 pivot_root unshare setns clone clone3. Verified in the Debian 12 VM: the narrower filter passes the bwrap probe (exit 0), the service starts with "sandbox bubblewrap ...", real uploads still give clean 200 / eicar 422, and systemd-analyze security is unchanged at 2.4 OK. The docs table row and the unit block both updated, and the closing caveat rewritten to explain WHY the explicit list is preferable — @mount is systemd-maintained and can WIDEN on upgrade, whereas an explicit list can only be narrowed by a future systemd, which fails closed.'
