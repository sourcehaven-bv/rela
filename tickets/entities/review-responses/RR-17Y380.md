title: The store index now contradicts a published audit claim
finding: An audit row says relation R1 was deleted while ListRelations still returns it until restart

resolution: Fixed. The store now prunes index entries for the relations it actually removed (new forgetRelations helper) before returning the partial result on both abort paths. The index-vs-disk divergence pre-existed, but this change makes it materially
worse rather than merely more visible.

**Before:** the index listed relations whose files were gone. Self-consistently
bad — nothing had asserted otherwise, and a reload reconciled it.

**After:** an audit record durably states relation R1 was deleted, while
`s.relations` still contains R1 and `ListRelations` returns it to the next
caller in the same process. That is an externally-visible claim contradicting
live queryable state, persisting until restart. On the attachment path (see the
attachment finding) `s.attachments` has also been mutated while `s.entities` has
not, so the index is not even internally consistent.

The store knows exactly which entries came off disk; pruning them before
returning the partial result costs one slice of `relationMeta` alongside the
`*entity.Relation`.
