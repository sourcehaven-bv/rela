title: RunPage matches() error abort is untested and diverges from Run's continue-on-error semantics
finding: 'internal/store/graphquerynaive/naive.go:110-113. RunPage aborts the whole page when matches() errors; Run (naive.go:57-63) yields the error and CONTINUES to the next candidate. Two implementations of one contract with opposite failure behavior, on the ACL read path. Verified untested by mutation: replacing the abort with `continue` survives the entire ./internal/store/... ./internal/acl/... suite with zero failures. matches() calls ListRelations, which on fsstore does real disk I/O, so a single unreadable relation file is the difference between ''short page'' and ''error''. A short page with an empty NextCursor is indistinguishable from end-of-results, so swallowing here would silently truncate an ACL-filtered list.'
severity: critical
resolution: 'Confirmed the reviewer''s mutation independently: replacing the abort with `continue` survived ./internal/store/... and ./internal/acl/... with zero failures. Added TestRunPagePropagatesMatchError (naive_test.go) using a new relErrReader that lists entities normally but fails every ListRelations, so the error surfaces from inside matches() rather than the entity scan errReader already covered. Re-ran the same mutation: now caught (--- FAIL: TestRunPagePropagatesMatchError). Kept the abort rather than aligning with Run''s continue-on-error, and documented why on RunPage: once results are bounded, a short page with an empty NextCursor is indistinguishable from end-of-results, so skipping an entity silently truncates an ACL-filtered walk into ''those entities do not exist''. The godoc explicitly names Run''s continue-on-error as arguably wrong for the same reason but out of scope here — its callers consume a full iterator and can observe the error mid-stream. Filed as a note in the comment rather than changing Run''s behavior under this ticket.'
