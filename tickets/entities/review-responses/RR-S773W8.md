title: Worker lock is taken per run, not held by one leader; cooldown, dirty state and reconcile cost break across processes
finding: 'internal/appbuild/realtime_worker.go:343-435 (run, triggerRound, reconcile) with realtimeLeaderLock (TryKeyedLock / filelock.TryLock per call). Plan sections 12 (D1) and 13 say one leader holds the lock for its lifetime and others take over on release. Here every tick, minute sweep and reconcile timer does its own TryLock, so on postgres (or desktop + server on one fs dir) the processes alternate holding it. Consequences: (1) D11 cooldown is per process: A posts a change at t0 and records lastPost in memory; the next change at t0+10s is picked up by B, which has no lastPost, and posts at once. The same holds for ids A postponed in `deferred`. (2) Each process''s reconcile timer fires on its own and each one succeeds whenever the lock is momentarily free, so N nodes run N full scans every 15 min. (3) Any overlap (two ticks at once, or a tick during another node''s minute sweep) sets leading=false and Drop()s; the next successful run does a full reconcile, so under steady writes overlaps cause repeated full scans of every trigger type. Fix: hold the leader lock for the worker''s lifetime as decided: acquire at start, keep it while running, retry acquisition on a timer when not leader, run Note/rounds/reconcile only while leading, and reset in-memory state (pending, deferred, lastPost, failures, dirty) on takeover. Add a test with two workers over one lock that shows the cooldown holds and only the leader reconciles.'
severity: significant
resolution: The worker now takes the lock once and holds it until it stops; followers only retry the lock every 10 seconds or on a wake. Cooldowns, retries, queues and unsaved shards live with the one leader, and a reconcile runs only when a process takes over.
status: addressed
