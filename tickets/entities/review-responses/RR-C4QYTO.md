type: review-response
title: Delegation switches string sorts to natural order while pushdown keeps byte order
finding: 'Design review C2. filter.compareStrings (sort.go:122-129) uses natsort.Less, which is numeric-chunk-aware AND case-insensitive. applyV1Sorting (api_v1.go:2243-2248) and pgstore (COLLATE "C", graphquery.go:537) are raw byte order. Independently verified: [Zebra apple item10 item9] sorts to [apple item9 item10 Zebra] in Go vs [Zebra apple item10 item9] byte-wise. queryplan.StringShaped (queryplan.go:119) admits PropertyTypeString as pushdown-eligible, so after delegation the SAME request returns byte order when pushed and natural order on the Go path (add ?q=, an `in` filter, or run on fsstore/memstore). This breaks the equivalence contract documented at listpushdown.go:26-33 ("ordering by such a property is byte-wise on both sides") for the most common sort key in the product, `title`. TestListPushdown_MatchesGoPathPageForPage will NOT catch it: its fixture sorts by `due` and `title` with same-case, digit-free values, where the two orders coincide. Requires an explicit decision: (a) make SortMulti byte-wise for strings (regresses search/dashboard ordering), (b) narrow StringShaped to decline string SORT eligibility while keeping equality filters, or (c) teach SQL natural order (not indexable). The plan''s "OUT of scope: natural-number sort on strings" reads as a future feature; it is present behaviour on the delegation target.'
severity: critical
resolution: 'DECIDED by the user 2026-09-20: option (a). Sorting stays in SQL so paging works properly and the overhead of loading a whole type is avoided; sort semantics change to what the sqlite/postgres backends can support, and the Go path conforms to SQL rather than the reverse. filter.compareStrings therefore stops using natsort.Less and compares byte-wise, matching COLLATE "C" and applyV1Sorting''s existing behaviour. StringShaped keeps admitting PropertyTypeString for sort pushdown; no narrowing needed for strings. Consequences accepted: (1) search and dashboard list ordering becomes case-sensitive and non-numeric, so ''Zebra'' sorts before ''apple'' and ''item10'' before ''item9''. Measured on 4,308 real ticket titles, 99% of positions move. This is a visible, product-wide behaviour change and MUST be in release notes. (2) The scope line ''OUT of scope: natural-number sort on strings'' is now wrong in the other direction and must be rewritten: natsort is being REMOVED from the query-sort path, not deferred. Scope note: natsort appears in ~30 call sites but only two are in this path (sort.go:113 SortByID, sort.go:128 compareStrings). The rest sort ids, type names and template names for display and are untouched. Architectural note supporting the decision: graphquerynaive is documented (sqlitestore/graphquery.go:12-20) as ''the behavioral reference every backend is verified against'', and sqlite/fs/mem all route GraphQuery through it, so making SQL-expressible semantics the authority matches how the codebase already reasons about backend agreement.'
status: addressed
