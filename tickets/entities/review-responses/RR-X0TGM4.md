title: 'Version hash is type-blind: %v collapses int64/bool/list to the same digest as their string form'
finding: 'store.VersionOf (internal/store/version.go:130) hashes each property value as fmt.Sprintf("%v", v). %v renders int64(1), float64(1), the string "1" and 1.0 all as "1"; true and "true" identically; []string{"a","b"} and the string "[a b]" identically. VERIFIED by probe against the real function: 5 of 6 type pairs tested collide. Consequence: a write that changes ONLY a property''s Go type produces an UNCHANGED version token, so a concurrent CAS that should conflict silently succeeds and the other writer''s change is lost. That is precisely the lost-write this ticket exists to prevent, on the narrow-but-real path where a value''s type changes without its rendering changing. Reachable because there is no coercion layer normalising property types on the write path — a Lua script writing 1 (number) where a form previously wrote "1" (string) is an ordinary occurrence, and sync/import paths can differ from the API path in the same way. What is NOT wrong and should not be changed: keys are sorted before hashing and every field is length-prefixed via writeVersionField, so map-iteration order is stable (verified over 200 rehashes) and a value cannot be crafted to look like the start of the next field. The defect is only the type-blind rendering of the value itself. Fix: include the value''s type in the hashed field, or render values through a canonical type-tagged encoder (e.g. hash a type tag byte then the value, or marshal via a canonical JSON encoder that preserves type distinctions) rather than %v. Add a table test over the colliding pairs above — it must fail before the fix.'
severity: significant
resolution: 'Fixed in 58939a52 on feat/store-cas-TKT-34XS2R. VersionOf now hashes the value''s TYPE alongside its rendering (fmt.Sprintf("%T", v) as a length-prefixed field before the %v field), so int64(1), float64(1) and "1" produce distinct tokens, as do true/"true" and a []string vs its bracketed form. Verified failing-first: removing the %T field makes TestVersionOf_DistinguishesValueTypes report all 5 collisions; restoring it returns the package to green. A companion test, TestVersionOf_StableAcrossInsertionOrder, pins the other half over 100 rehashes — equal content must still hash equal despite randomised map iteration — so a future ''fix'' cannot trade type-sensitivity for spurious conflicts. All four backends re-verified green with the new derivation, including pgstore against live PostgreSQL 15 (33s) and the full storetest conformance suite. Sorting and length-prefixing were already correct and were left untouched.'
status: addressed
