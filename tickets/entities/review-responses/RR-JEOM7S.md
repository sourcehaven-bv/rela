title: Busy row ceiling is a pre-gate count for cardinality-one types
finding: 'internal/realtime/busy.go:175-181 sets the ListWaiting ceiling to one row per anchor for a cardinality-one type, and :104-108 turns ErrTooManyRows into an error, so internal/dataentry/busy_rows.go:54 drops _busy for the whole page. The comment says no stored channel set reaches the ceiling, but nothing enforces one stored channel per anchor for a one type: the per-anchor cap (sqlchannels/sql.go:845, filechannels/ops.go:493) counts only named channels and only at create, so named channels left from an earlier cardinality: many config (or a singleton beside 200 named channels on a many type) exceed it. ListWaiting counts before the read role is applied, so a caller who lacks the type''s read: role sees _busy absent instead of [] when the page''s anchors hold more working channels than the ceiling. That is a one-bit page-level signal about channel state the caller may not read, and it also makes the feature fail closed for everyone on that board. Precondition: an operator changed the type''s cardinality (or a one-to-many switch left a singleton) and enough of those channels are in a working state; unverified end to end. Fix: take the ceiling as len(anchors)*(realtimelimits.MaxChannelsPerAnchor+1) for every cardinality, so the singleton plus the full named cap always fit, and raise the clamp or cap per_page so 100*201 fits under channels.MaxWaitingRows; alternatively, for a cardinality-one type pass the name-'''' restriction into the WaitingQuery so leftover named channels are never counted. Add a TestBusy case with leftover named working channels on a one type that asserts ok=true.'
