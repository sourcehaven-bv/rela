title: _position navigated the default scope, not the list's
finding: ScopeDescriptor carried source/type/filters/sort/q but not the view's query_scope, and its toQuery() rebuilds the list's query from those fields alone. So prev/next resolved against the entity type's DEFAULT scope regardless of what the originating list showed. On a list scoped to `archief`, the entity the reader has open is absent from the default set, so the endpoint answers 404 not_in_scope for the very row being looked at; the inverse makes prev/next walk rows the list never showed. The doc comment claiming 'the keys match exactly what handleV1ListEntities reads' had become false.
severity: significant
resolution: 'Added QueryScope to ScopeDescriptor and emitted it from toQuery(), plus query_scope on the TypeScript ScopeDescriptor and in buildListScope. TestQueryScopes_PositionMatchesTheScopedList pins both directions: the archived row resolves 1/1 within `archief`, and is still correctly refused under the default. Verified by mutation — dropping the toQuery line reproduces the 404 exactly.'
status: addressed
