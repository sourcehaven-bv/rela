title: Unbounded N+1 in applyRelationFilters over full unpaginated set every request
finding: Pagination happens after scopedSortedEntities, so applyRelationFilters runs over the entire type's visible set before slicing to a page. For N entities and M relation filters it does O(N·M) ListRelations plus a GetEntity per neighbor edge, uncached, every list request and every _position nav. A 5k-entity type with one relation filter is 5k ListRelations + a GetEntity per edge on every keystroke-driven refresh. No cap, no batching, no short-circuit; on fsstore this is disk/parse per neighbor. At minimum note the ceiling; better, resolve candidate-set titles in one pass or push the filter into the store query. api_v1.go:321,:350.
severity: significant
resolution: matchRelationFilter short-circuits (stops scanning a row's edges on first readable title match) instead of building the full title slice. The O(N·edges) pre-pagination ceiling is now documented in the applyRelationFilters godoc, with store-side pushdown noted as the future optimization. Bounded + documented per the finding; full pushdown deferred. Commit 72f10b99.
status: addressed
