title: CAS PATCH migration passed a bare id, silently authorizing and writing the default face
finding: '[security] Found while merging develop into feat/store-cas-TKT-34XS2R, not by the reviewers. The PATCH migration called h.manager.PatchEntity(ctx, entity.ID, patch) with the BARE id. Since develop''s content-states work (FEAT-9CD2MX / TKT-DOFYR1) an id addresses a FAMILY of state rows, and PatchEntity resolves the face from the row it loads by that id — so a bare id lands on the DEFAULT face. Two consequences, both wrong: (1) authorization is decided against the default state rather than the one being written, so an explicit face-scoped grant such as policy@published stops matching — observed as PATCH POL-1@published returning 403 ''no role grants update on type policy'' with a grant that should permit it; (2) worse in the other direction, a caller permitted on the default face would have their write APPLIED to the default row while they addressed a faced one. The pre-existing UpdateEntity path is unaffected because it passes the whole entity, so e.Face reaches translateVerb (write_handler.go:972). PatchEntity itself is correct and even documents this exact trap (''Face from the STORED entity, not from id: id may be the fused boundary form, and authorizing without it would decide against the default face'') — the defect was purely in what the caller handed it. Caught by develop''s own TestFacedIDWrite_ExplicitFaceGrantStillWorks, which passes on clean develop and failed on the merged branch; that test is the reason this did not ship.'
severity: significant
resolution: 'Fixed: the handler now builds the fused state ref with entity.FormatStateRef(entity.ID, entity.Face) and passes that to PatchEntity, so the face survives to both the authorization subject and the row that is written. Verified against develop''s TestFacedIDWrite suite: failing before the fix (403 on an explicitly granted face), both cases green after. Comment at the call site records why the bare id is wrong, since the signature takes a plain string and the mistake is invisible at the type level.'
status: addressed
