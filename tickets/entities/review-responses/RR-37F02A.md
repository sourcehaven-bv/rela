title: A lost postgres session leaves two leaders for good, so every trigger post is duplicated until a restart
finding: 'internal/appbuild/realtime_worker.go run/lead (and pgstore.TryKeyedLock). The leader takes the advisory lock once on a pinned pool connection and never uses that connection again. If the server drops that session (idle_session_timeout, a pgbouncer or proxy idle cut, a TCP reset, a failover), the lock is freed and a follower takes it within realtimeTakeoverInterval, but the old leader cannot notice and leads on until it is restarted. Both processes then note every change, both process it and both post before either saves, so each trigger message is posted twice, indefinitely. Their whole-shard saves are last-writer-wins, so each also overwrites the other''s seen data and reconciles repost what was lost. The comment ''The triggers stay correct, because what they have seen is shared in the KV and a post is at least once'' understates this: at-least-once covers a crash window, not a permanent second writer. An idle pinned connection is the most likely one to be cut, so this is not only a failover case. Fix: have the leader check the lock while it leads, for example on the takeover ticker run SELECT 1 on the pinned connection (or check pg_locks for pg_backend_pid()). On error it steps down: return from lead, which runs Reset, destroy the connection, and go back to the follower loop. This needs leaderLock to return a liveness check or a lost channel next to release. A test can use a lock whose check fails, and assert that the worker stops noting changes and tries the lock again.'
severity: significant
resolution: pgstore.TryKeyedLock now returns a HeldLock whose Check does a round trip on the pinned session and destroys the connection on failure. The leader runs the check every takeover interval, steps down on failure (Reset, release) and goes back to trying the lock, so two leaders overlap for at most 10 seconds. TestTryKeyedLock_LostSession terminates the backend and TestRealtimeWorker_StepsDownOnLostLock covers the worker.
status: addressed
