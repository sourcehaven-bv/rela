## Finding

`writeBackGuard.ts` returns `drift-blocked` when re-serializing would change
what the document means. Refusing to write is correct — the alternative is
corrupting the file. Refusing *silently* is not.

Nothing consumed the verdict. The user would keep editing, press save, and get a
success state over an unchanged body.

## Resolution

`reportDrift()` raises `uiStore.error(...)` on the same channel `DynamicForm`
already uses for load and save failures. The message says the content could not
be saved safely, that the edit was not applied, and asks the user to report it —
because reaching this state means the serializer has a bug worth hearing about.

Latched with a `driftReported` flag reset on each document load: the condition
persists until the document changes, so firing per keystroke would bury the page
in toasts.

Note this was unobservable before the two criticals were fixed — the verdict was
never computed on the production path at all.
