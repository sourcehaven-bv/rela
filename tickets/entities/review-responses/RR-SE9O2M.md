title: asserted_by still comes from $USER on the shipped Linux binaries
finding: 'assertingUser (internal/cli/identity.go) calls os/user.Current. Every release binary is built with CGO_ENABLED=0 (.goreleaser.yaml, justfile), so on Linux os/user uses lookup_stubs.go: it parses /etc/passwd only, and when the uid is not there it returns User{Username: os.Getenv("USER")} without an error, as long as $HOME is set. A uid that is missing from /etc/passwd is common: SSSD/LDAP/AD accounts (pure Go does not query NSS), and containers or CI runners started with an arbitrary --user. On such a host, `USER=alice rela --run-as system:ci update X ...` still records asserted_by=alice, which frames a person. `USER=system:realtime` gives asserted_by=system:realtime in the same way. The resolution says "no environment variable is read", but that is false for these builds. TestAssertingUser stubs lookupOSUser, so it cannot detect this, and macOS takes the libSystem path, which hides the problem on developer machines. Fix: use user.LookupId(strconv.Itoa(os.Getuid())). Its stub implementation reads /etc/passwd only and does not fall back to $USER. On error, keep the uid:N fallback. Add a test, guarded by an osusergo build or a check of the Go fallback, that sets USER to a different name and asserts the name is not returned for a uid that is not in /etc/passwd.'
severity: significant
resolution: 'user.LookupId alone does not fix it: for the process''s own uid it returns user.Current, which still falls back to $USER in the stub build. accountName now reads /etc/passwd itself where os/user has that fallback (cgo-free non-darwin builds and osusergo, selected by build tags), and uses user.LookupId elsewhere. A missing uid gives uid:N. Tests: TestPasswdName (spoofed USER, missing uid, missing file) and TestAccountName_NoEnvFallback, also run with -tags osusergo and CGO_ENABLED=0; the linux CGO_ENABLED=0 build vets and lints.'
status: addressed
