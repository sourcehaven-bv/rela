title: SQLite's case-insensitive LIKE lets Rename and DeleteAllFaces reach an unnamed entity
finding: 'sqlitecomments reached faced threads with `target_key = ? OR target_key LIKE ? ESCAPE ''\''`. SQLite''s LIKE is ASCII case-INSENSITIVE by default while "=" is byte-exact, so the two arms of one query matched different row sets — and a different set again from pgcomments, whose column is COLLATE "C" and whose LIKE is case-sensitive. Verified directly: DeleteAllFaces("tkt-1") deleted TKT-1@draft''s comments, and Rename("tkt-1", "OTHER-9") merged two authors'' threads. Reaching the bad rows requires two entities differing only by case to coexist, which the entities_id_lower_key index currently forbids — so this was unexploitable rather than harmless. The residual risk was that a correctness property of the comment backend was supplied by an invariant in a package it deliberately does not import, undocumented at either site and pinned by no test, while sqlitestore/rename.go had already hit the same hazard and handled it with an explicit EqualFold guard plus a comment saying the folding must be deliberate rather than silent.'
severity: significant
resolution: Added a byte-exact substr(target_key, 1, ?) = ? guard beside the LIKE in both Rename and DeleteAllFaces, so the two arms agree and both backends answer alike. Chosen over COLLATE BINARY, which does not affect LIKE at all (verified — the column collation was applied and LIKE still folded), and over PRAGMA case_sensitive_like, which is global and would silently change sqlitestore's queries where the folding is deliberate. The LIKE stays because it is what the index serves; substr only filters rows it already narrowed to. Pinned by the new commentstest.RunKeyFidelityTests, run by the database backends only — filecomments cannot promise case-sensitivity on a case-insensitive filesystem, which is a sound decision for a file backend rather than a defect.
status: addressed
