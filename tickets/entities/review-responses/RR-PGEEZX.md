title: sort=id and sort=modified change public v1 API behaviour as refactor side effects
finding: 'Design review S5 and S6. filter.SortMulti treats "id" and "modified" as virtual properties (sort.go:210-213). applyV1Sorting has neither concept. (1) sort=id: SortMulti routes to SortByID -> natsort.Less, giving [TKT-1 TKT-2 TKT-10]; applyV1Sorting finds no Properties["id"], treats every row as absent, and falls to its byte-wise id tiebreak giving TKT-1, TKT-10, TKT-2. The plan says "the tiebreak must be byte order, not natsort - do not reuse SortByID", which is right for the IMPLICIT tiebreak but silent on the EXPLICIT sort=id key, and an implementer could read it as licence to change SortByID itself, silently reordering every search result and CLI listing. These are two separate decisions and the plan conflates them. Note sort=id is not pushdown-eligible (stringShaped("id") fails since id is not in def.Properties), so it is Go-path-only with no differential test to catch the change. (2) sort=modified: today a no-op on the v1 path (no such property, order preserved); after delegation it starts actually sorting IF the Accessor populates Record.ModifiedAt. The plan never mentions writing an Accessor. The v1 list path serves content-free header rows, so whoever writes it must decide what ModifiedAt maps to on entityPkg.Entity (filter/sort_test.go:12 uses UpdatedAt). Left zero, every row sorts as absent and is then scrambled by RR-6F2UF2''s descending inversion. sortByModified also has that defect and no id tiebreak.'
severity: significant
status: open
