title: A relation can be filed at a declared face whose source row does not exist
finding: 'requireRelationFaceFor validates a named face against the entity TYPE''s declaration (def.Faces), never against whether the source row exists at that face; anyFaceOf then confirms only that the entity exists at SOME face. So with beleid declaring {concept, vastgesteld} and POL-3 existing only at concept, CreateRelation(POL-3, citeert, SRC-9, {FromFace: ''vastgesteld''}) succeeds and stores POL-3@vastgesteld--citeert-->SRC-9. Creating the vastgesteld face later makes the pre-planted edge appear as a normal edge of that face. Not an authorization bypass — GrantsVerbOnState is exact-match on the face, so the planter already holds the grant on the very face they plant at and could write the same edge a second after the face exists. Unreachable from HTTP only by accident of shape: relations_modern.go:303 derives the tail from addr.Face, which provably exists. Lua is the first caller supplying the face as free input.'
severity: minor
reason: 'Deferred as a separate ticket rather than fixed here, for three reasons. (1) It is an integrity/UX defect, not a confidentiality or authorization one — the security reviewer rated it minor and could not construct an escalation. (2) The fix belongs at the CreateRelation call site (an existence check via GetEntityState against the NAMED face, replacing anyFaceOf''s any-face lookup), which changes error behaviour for peers generally and deserves its own test matrix and error-shape decision — it should surface as ErrEntityNotFound ''source POL-3@vastgesteld not found'' so the SPA maps it like a dangling peer. (3) Folding it in would repeat this ticket''s own mistake: the critical regression here came from widening entitymanager validation without checking every caller, and an existence-at-face requirement has exactly the same blast radius. Worth a ticket because the surrounding design is emphatic that a faced write names a row that exists.'
status: deferred
