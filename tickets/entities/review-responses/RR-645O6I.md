title: Relation conflict surfaced as ErrEntityAlreadyExists — wrong sentinel, relation-specific one exists downstream
finding: 'createRelation (rename.go:225-226) maps a relation store.ErrConflict to rename.ErrEntityAlreadyExists with a from--type-->to payload. entitymanager/rename.go:26-27 then translates that to entitymanager.ErrEntityAlreadyExists. But entitymanager already defines a distinct ErrRelationAlreadyExists (errors.go:54) used by the direct relation-create path and mapped to its own HTTP status/message by the sync layer. So a renamed-relation conflict is reported to an API client as an ENTITY conflict, with a nonsense message (''entity already exists: REQ-9--addresses-->DEC-1'' — that key is not an entity ID) routed through the wrong branch of the caller''s error taxonomy. Unreachable under single-writer, but this PR''s whole point is the multi-writer backend where it can fire. Fix: add rename.ErrRelationAlreadyExists, return it from createRelation, and extend the entitymanager/rename.go switch to map it to entitymanager.ErrRelationAlreadyExists.'
severity: significant
resolution: 'Resolved by the re-route (RR-PUI4JF): the internal/rename package and its createRelation helper are deleted, so there is no longer a rename-path relation create that could surface the wrong sentinel. Relation re-keying now happens inside the atomic store.RenameEntity; a target-ID conflict is reported once, as ErrEntityAlreadyExists for the entity newID (correct — the conflict is on the entity ID being renamed onto, not a relation).'
status: addressed
