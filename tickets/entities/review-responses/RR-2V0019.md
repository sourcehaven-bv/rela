id: RR-2V0019
type: review-response
title: CRLF injection into iCalendar via property-referenced RRULE
finding: 'The RRULE line is emitted unescaped: ical.go:76 does writeLine(&b, "RRULE:"+e.RRule). escapeText (which neutralizes CRLF) is applied to SUMMARY/DESCRIPTION/UID/URL but NOT to RRULE. When rrule is configured as a property reference (resolveRRule''s non-''='' branch, feed_provider.go:239), the value is read raw from the entity via e.GetString(cfg). Config validation only checks the property exists, never its value. Failure: a feed configured with `rrule: schedule` (per-entity property) lets any user who can write that property (data-entry API, MCP, hand-edited markdown) set it to `FREQ=DAILY\r\nBEGIN:VALARM\r\nACTION:AUDIO\r\nTRIGGER:PT0S\r\nEND:VALARM`, injecting arbitrary iCalendar content (VALARMs, VEVENTs, overwritten fields) into the served feed for every subscriber. Reachable via the LIVE GET /api/v1/_feeds/{name}.ics List path. Fix: sanitize CRLF at the writeLine choke point (structural invariant) AND/OR validate the resolved RRULE via rrule-go at render time, skipping on failure.'
severity: critical
resolution: 'Fixed at the choke point (L1): writeLine now strips raw CR/LF via stripLineBreaks before folding, so NO field can inject iCalendar lines — folding is the only legitimate CRLF source. Defense-in-depth: resolveRRule also validates the resolved rule via rrule-go and drops it if invalid. Pinned by TestRenderEvent_NoLineBreakInjection (calfeed) which asserts a CRLF-bearing RRULE collapses to one line with no injected VALARM.'
status: addressed
