title: Playwright worker comment overclaimed isolation; postgres container and CPU are shared
finding: 'The comment added beside `workers: 4` asserted that ''every shared resource is already per-worker''. That is stronger than what the code provides. Per-test state is isolated (ephemeral port, mkdtemp dir, pid-keyed schema), but the postgres:16 service is a single container every worker''s server pools against, and the runner''s 4 cores now carry roughly 8 CPU-hungry processes (Chromium plus rela-server per worker) against 5s action and 10s navigation timeouts. With retries: 2, load-induced flake passes on retry and reports green, so the cost surfaces as wall-clock regression rather than a visible failure. A future reader would have built on a safety property that was never real.'
severity: minor
resolution: 'The reviewer''s concern was correct and the worker count is reverted to 2. Raising it to 4 was tried over two CI runs: the first passed, the second failed all 12 tests in document-edit-button.spec.ts. The failure is NOT the predicted timeout flake — the page rendered promptly showing ''No document content available'', meaning the document''s `command: ["cat", "{in}"]` renderer failed. That renderer goes through cmdexec under bubblewrap and fails closed, and internal/dataentry/document.go:720 builds its runner without WithMaxConcurrent (unlike internal/transform, which bounds conversions at 4), so ~8 busy processes on 4 cores broke sandbox setup. Both retries were burned, so retries:2 did not even mask it. Reverting costs ~50s of the ~345s saved; the rest of the win is independent of it. The config comment now records the evidence and names the unbounded runner as the prerequisite for ever raising this. Filed as TKT-LP4EE8.'
status: addressed
