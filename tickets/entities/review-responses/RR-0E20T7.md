title: 'iCalendar correctness: DTSTAMP clock injection, UID uniqueness, and CRLF/fold edge cases need explicit test pins'
finding: |-
    The hand-rolled iCalendar approach is sound (no vendor for a small format), and AC1-5 cover the main correctness surface. Tightenings before implementation:

    1. DTSTAMP: plan correctly injects `now` into feed.Render for determinism. But the HANDLER path calls a real clock — ensure the handler passes a real time.Now() while tests pass a fixed clock; don't let a package-level time.Now() sneak into ics.go (would break the pure-renderer property and CLAUDE.md's determinism).

    2. UID stability vs uniqueness: UID = entity-id@domain is stable (good for calendar dedup across polls). But if a script emits two events for the same entity (e.g. a task with due AND a review date), UIDs collide and calendars will merge/overwrite them. Either document 'one event per entity' or let the script supply a UID discriminator (uid = id .. ':due'). Add a test.

    3. Fold + CRLF: AC4 covers >75-octet fold and escaping. Add explicit pins for: a value exactly 75 vs 76 octets (off-by-one boundary), a multi-byte rune straddling the 75-octet boundary (must not split mid-rune — fold on octet count but never inside a UTF-8 sequence), and that the whole document is CRLF-terminated including the final END:VCALENDAR (some parsers reject a trailing bare LF).

    4. Empty feed: AC edge cases mention 'zero events = valid empty VCALENDAR' — confirm a VCALENDAR with zero VEVENTs is what Apple/Google accept (it is), and pin it.
severity: minor
resolution: 'Folded into the plan''s acceptance criteria and edge cases (PLAN-6LOL0Z AC1-5 + Edge Cases): DTSTAMP via injected clock (no time.Now in the pure renderer), UID discriminator when >1 event per entity, 75/76-octet fold boundary, multibyte-rune fold safety, CRLF-terminated final line, and empty-feed validity are now explicit test pins.'
