title: migrate rename has a TOCTOU window and unspecified ordering vs content migrations
finding: 'The plan specifies the rename as ''a distinct pre-step before the per-file migration loop'' but leaves two things undefined. (1) TOCTOU: the stated guard is ''if the target exists, skip the rename''. storage.FS.Rename (internal/storage/fs.go:28) is an os.Rename wrapper, which on POSIX silently REPLACES an existing target atomically. A stat-then-rename sequence therefore has a window where a concurrently-created schema.yaml is destroyed, and more practically, any bug in the guard means silent overwrite of the user''s new file rather than an error. Since the trust boundary here is the operator shell this is low-severity as an attack, but as a correctness matter the guard must be treated as advisory and the failure mode chosen deliberately — prefer refusing to rename when the target exists and returning an error the operator can act on. (2) Ordering: the rename mutates ctx.SchemaPath, which the very next loop iteration uses via getMigrateFiles(). The plan does not say whether the content migrations then run against the OLD or NEW path, nor whether the Context is rebuilt. If the rename happens first and getMigrateFiles() was already evaluated (it takes ctx and is called once, migrate.go:102), the loop will migrate a path that no longer exists and silently skip it via the stat-guard at line 106 — meaning a legacy project gets its file renamed but its content migrations silently NOT applied. That is a real ordering bug latent in the plan as written.'
severity: significant
resolution: 'Plan updated. Ordering is now specified as load-bearing in approach step 5: rename FIRST, then update ctx.SchemaPath, then evaluate getMigrateFiles(ctx) — preventing the stat-guard at migrate.go:106 from silently skipping content migrations on a renamed project. AC-6 was strengthened to assert both effects (rename AND content migration) in a single run rather than the rename alone. The TOCTOU/replace-semantics issue is documented in Security Considerations with the chosen failure mode: refuse the whole operation when the target exists, since os.Rename replaces silently on POSIX and a stat-first guard is advisory only.'
status: addressed
