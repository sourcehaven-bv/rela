title: Duplicate-target refusal blocks configs that cannot be merged, and its advice is wrong
finding: 'Plan step 3 refuses a second entry with the same `to` and tells the author to "merge the two with one when (use or)". A guard cannot read the poster: sessionGuardEnv (internal/realtimecfg/session.go:626-652) declares only `message` (props only, programs.go:57-74), `session` and the stdlib. So two entries that differ only by poster rule, such as [{to: working, roles: [lead]}, {to: working, when: "message.urgent"}] ("a lead moves it; anyone else only when urgent"), cannot be written at all, and the advice cannot be followed. (from,type,to) only has to be unique for entries whose mark matters, meaning entries with outputs: resolveMark (outputs.go:510-540), personMark/triggerMark (outputs.go:348-387) and the gate only read outputs and job. Fix: refuse a duplicate `to` only when either entry has outputs, and let TransitionTo return the first entry with that target. Otherwise reword the reason so it states the real limit and drop the "use or" advice for entries that differ by roles/by.'
severity: significant
resolution: Duplicate `to` is now refused only when either entry has outputs, the reason no longer suggests "use or", and `TransitionTo` returns the first entry with that target.
status: addressed
