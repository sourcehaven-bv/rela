## Finding

The plan proposed re-adding an affordance that was **deliberately removed**, and
did not know it.

TKT-651W (`done`, implements FEAT-K111 "Entity views are strictly read-only")
removed `+ Add` / `Link Existing` from the entity detail page's relation
sections. Its reasoning:

> The detail view is a **read** surface — the same screen used to browse, navigate,
> and inspect an entity's neighbourhood. Editing the graph from inside a read view
> blurs the line between viewing and editing, and duplicates affordances that already
> exist in the dedicated form path.

Its "Proposed change" names the exact call this plan proposed to re-add: "drop
the `resolveSectionButtonsWithTraverse(...)` call in the view handler... Keep
the call in the side-panel handler."

The invariant is enforced, not merely recorded:

1. `internal/apiwire/v1/responses.go:1088-1092` — "Do not reach for this type from a
new view-related response: the read-only-view invariant established by TKT-651W
means no view section should carry add affordances." This directly forbids the
plan's §3, which named `ViewAddInfo` "the natural carrier".
2. `internal/dataentry/api_v1_test.go:4020` `TestV1Views_NoAddOrLinkInfoOnSections` —
five sub-cases across outgoing/incoming × cards/list/table plus the no-form
variant, hardened by RR-O8FM specifically against a partial re-introduction.
3. `internal/dataentry/sections.go:429-435` — the side-panel-only doc comment, written
by RR-EIXM so "future readers understand why entity-detail view does not call
it."

The plan called this "works, but only reachable from `_sidepanel`" — framing a
deliberate removal as an incidental limitation. RR-R8X6 predicted precisely
this: the `ViewAddInfo` name "lies about scope" and "a future contributor might
wire 'ViewAddInfo' into a new view-related response because the name suggested
it was generic."

## Resolution

Escalated to the user rather than resolved unilaterally, since reversing a
design-reviewed decision is not a decision to make inside a plan.

**Outcome: honour the invariant.** Default-on is withdrawn. The detail page
stays read-only by default; create buttons are strictly opt-in via an explicit
`create:` block per section. This is a narrow relaxation — "read-only unless an
operator asks otherwise" — rather than a reversal.

Consequences now folded into the plan:

- The guard test **narrows rather than inverts**: it must keep asserting absence for
sections with no `create:` block, and gain cases asserting presence only where
one is configured. It remains a live guard against accidental re-bleed.
- FEAT-K111 is **not** superseded. The ticket records that it relaxes the invariant
only under explicit opt-in, and must cite TKT-651W so the next reader finds the
history that this plan missed.
- The three enforcement comments are updated to state the narrowed rule, not deleted.
