title: SetSchemas blocks on txMu while holding mcpServices.mu
finding: 'internal/cli/mcp_wiring.go:180. RefreshStoreSchema waits for txMu, and an open Tx can run a long automation cascade. While it waits it holds s.mu, so Close, Deps, republish and current() all stall behind that Tx. No current Tx callback takes mcpServices.mu, so this is a stall, not a deadlock. It becomes a deadlock as soon as one does. The lock order txMu then mu inside fsstore matches every other write path and is fine. Fix: document on reload that refresh must not run under mu if Tx callbacks may ever reach mcpServices, or restructure so publish and refresh happen under a dedicated reload mutex rather than the mutex readers use.'
severity: minor
resolution: The store refresh runs outside mcpServices.mu; reloadMu serializes whole reloads so an older reload cannot refresh after a newer one.
status: addressed
