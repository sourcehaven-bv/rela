id: RR-R43942
type: review-response
title: RecordFailure(failures int) is a read-modify-write over the wire; the count can go backwards
finding: 'Passing a pre-computed failures count means the caller read it, incremented, and handed back the result — the lost-update pattern encoded in the signature. Worse, the store cannot validate it: a caller with stale state writes failures=2 over a row that says 5, and the ladder goes BACKWARDS, un-backing-off a persistently failing task so it oscillates between 5m and 40m instead of climbing. The store should perform the increment atomically and return the new count; the caller keeps ownership of retryDelay (a pure function of the count), so scheduling policy stays in internal/scheduler and storage stays free of it.'
severity: significant
resolution: 'RecordFailure(ctx, task, start) (failures int, err error) — the store performs the increment atomically and returns the new count, so no count crosses the wire inbound and it cannot move backwards. retryDelay stays in internal/scheduler: it is a pure function of the count and is scheduling policy, so the store owns the increment but never the curve. The failure path costs two calls (increment, then SetNextRetry), which is acceptable because failure is the rare path and the ladder floor is 5m.'
status: addressed
