title: 'State-tailed edges reach the write loop; a schema-level scope check is the wrong guard'
finding: 'collectRelations leaves RelationQuery.FromFace nil, which matches every tail (storeutil.go:306,334), and fsstore populates FromFace on every listed relation (relation.go:102). So content-scoped edges are in the slice. If the implementer copies rename_relation_type''s data construction (steps.go:537) the new RelationData omits FromFace, so every state-tailed edge is recreated at the DEFAULT tail and two edges differing only in tail collapse onto one key - the silent merge the ticket exists to prevent. The delete half is worse: DeleteRelation addresses the default-tail edge by contract (store.go:519-537), and that contract explicitly names deleting a DIFFERENT edge and reporting success as the bug DeleteRelationState was added to make unavailable. The plan''s only mitigation was a run-time check of scope: content against the LIVE metamodel, which is a proxy for the question that matters and can be stale: if scope was changed to identity while state-tailed rows remain stored, the check does not fire and the merge proceeds.'
