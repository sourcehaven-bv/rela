type: review-response
title: sort:modified silently stopped working on the search path
finding: 'Code review C1. queryservice.go swapped filter.SortMulti for filter.QuerySortApply, but SortMulti dispatched "modified" to sortByModified (reading Record.ModifiedAt) and QuerySort.compareKey only special-cased "id". So "modified" fell through to the property lookup, both rows compared absent, and every row tied straight through to the id tiebreak. Reproduced: sort:modified:desc over three rows with distinct ModifiedAt returned [A B C] instead of [B C A]. This is a documented, parsed, tested feature: docs/data-entry.md lists `sort:id / sort:modified` in the search syntax table, searchparser parses it and asserts on it in parser_test.go:237-245, and queryservice.go:190 wires those clauses to this exact call site. A user typing sort:modified:desc in the search bar got id-ascending with no error. My isVirtualSortProperty comment even named "modified" and argued no backend can order by it - correct for PUSHDOWN eligibility, and exactly the wrong conclusion for the Go fallback path, which holds a materialized result set and has no SQL to conform to.'
severity: critical
resolution: 'Fixed by honoring "modified" in compareKey: a zero time sorts as absent (last ascending, first descending, matching how an absent property behaves), otherwise time.Compare. Safe for path agreement because the pushdown planner rejects the key independently - stringShaped("modified") fails since no entity type declares a property with that name - so a request sorting on it stays on the Go path and cannot be pushed and reproduced differently. Added TestQuerySort_ModifiedOrdersByModificationTime covering both directions plus a never-modified row. Mutation-verified: removing the arm fails both assertions. The isVirtualSortProperty doc comment was rewritten - it now explains what the function is actually for (skipping rank resolution for non-property keys) rather than asserting an unsupported-ness that was never true of the Go path.'
status: addressed
