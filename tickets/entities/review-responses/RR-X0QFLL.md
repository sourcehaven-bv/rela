finding: 'internal/dataentry/live.go:767 and :791 pass only != nil to fallback, which exempts only inbox and busy subscriptions. A non-busy list or presence pair that sits in a topic round only because it is pending (left over from an earlier full-round cut, collect live.go:871 via due) still gets a fallback frame when the round overflows roundCap or roundBudget. Whether it overflows depends on how many other pairs the round selected. This diff adds other principals'' busy boards to that count, and they are selected by session moves on entities the observer cannot see (live_busy.go selectsBusy). So the observer''s frame count shifts with hidden moves. The class already existed through channel and inbox subscriptions of other principals, and the exploit is unverified: it needs a deployment near roundCap and an attacker who keeps pending pairs at the cut. It reveals that some change happened in the process, not which entity changed. Fix: in a topic round, park a pair that collect took only from due (not selected by only.selects or safetyDue) in pending with no markChanged; it already got its fallback frame in the round that cut it. Alternatively, record this as an accepted residual in the live_busy.go package comment next to the inbox round-duration note.'
