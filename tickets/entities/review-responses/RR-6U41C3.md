title: 'Step oscillates: a re-run reverses the edges back'
finding: 'collectRelations filters on relation TYPE only (steps.go:1104), and a reversed edge is indistinguishable in shape from an unreversed one. Verified empirically on a memstore before the review landed: reversing TSK-1--assigned-to-->PER-1 yields PER-1--assigned-to-->TSK-1, which the next collectRelations returns unchanged. A second run flips every edge back. This violates the Step contract stated at steps.go:21-24, where re-running IS the documented crash-recovery mechanism, so the recovery procedure would itself un-migrate the graph. rename_relation_type is idempotent only because its collection predicate (the OLD type name) stops matching after the run; a reversal leaves the type name untouched and so has no such predicate.'
severity: critical
resolution: 'Found independently and fixed in the plan before the review returned. Run now collects only edges still pointing the old way, using the endpoint entity TYPES as the directional test (an edge is already-reversed when its from-entity type is admissible under the to-shape). Consequence accepted and written into the plan: a relation type whose from-list and to-list share an entity type cannot be decided this way, so it is refused rather than silently oscillating on the ambiguous subset. Acceptance criterion 2 strengthened to assert direction, not just a zero count, since a count assertion passes for a step that reverses everything twice.'
status: addressed
