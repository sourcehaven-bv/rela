title: Per-message _actions go stale; edit-window expiry never reaches the client
finding: 'useChannel.ts follow() (187-206) only re-reads messages whose rev moved. Message `_actions` depend on time (edit_own.within, PendingRelease) and on policy (acl.yaml reload, role change), and neither bumps a message rev. A held message therefore keeps `edit` after its window closed and keeps `remove` after the role was revoked. It also never gains `release` once PendingRelease passes. A frame with no message refetches only the head. AC 10 (''edit disappears after the edit window'') holds on the server only, and the client has no way to schedule it, because neither the descriptor nor the message carries the window. Fix: put an `edit_until` (and `release_after`) timestamp on the wire Message so the client can drop or add the button with one timer for the soonest deadline. On a frame that brings no message (policy round, lifecycle), also refetch the held window, or at least the visible newest page.'
severity: significant
resolution: Messages carry edit_until and release_after, useChannel arms one timer for the soonest deadline and rereads that page, and a frame without messages rereads the newest page when state or head affordances moved or the type has no ephemeral messages.
status: addressed
