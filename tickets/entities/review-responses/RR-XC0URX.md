title: Cascade/automation scripts get allow-all reads implicitly — asymmetric with the write side's explicit AllowACLBypass opt-in
finding: 'The plan assigns appbuild''s build-internal readDeps (:680) → LuaScriptRunner allow-all, reasoning ''automation runs below the ACL boundary''. But automation scripts fire in response to a USER''s write and execute on that user''s request ctx, so a policy reader would naturally bind them to the acting user''s ACL. Meanwhile the WRITE side of the very same runtime requires an explicit per-action opt-in to bypass ACL (action.AllowACLBypass + ElevatedProvider, TKT-D8T148, luascriptrunner.go:88-95). Granting unconditional allow-all READS while writes need a declared flag is asymmetric and undocumented: an automation could read every hidden field in the graph and write it into a visible entity, with no operator opt-in and no audit signal distinguishing it from a scoped automation. Either (a) bind cascade reads to the acting principal like other request paths, (b) gate allow-all reads behind the same AllowACLBypass flag, or (c) keep allow-all but state the trust model explicitly (automations are operator-authored config, same tier as schedules) and log it. Decide deliberately — do not let it fall out of a default.'
severity: significant
resolution: 'Decided with the user (2026-07-24), resolving option (a): cascade/automation reads bind to the ACTING USER''s principal by default — symmetric with the write side. Escalation reuses the EXISTING sudo rather than a new mechanism: rela.bypass_acl''s `admin` handle gains read methods as a FOLLOW-UP ticket (user''s call), keeping this PR''s blast radius to the seam. Rejected: per-action `roles:` config (ambient authority for the whole script, invisible at the call site, duplicates the assignment mechanism, bypasses delegate-X tamper resistance). No read-side ACL bypass is added in this PR; an automation that relied on full reads surfaces as a real signal.'
status: addressed
