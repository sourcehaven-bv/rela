## Verification

`traverseViewRecursive` (`views.go`) — recurses through every immediate result,
raw store, no gate:

```go
immediate := a.traverseViewOnce(ctx, sourceID, rule)
for _, e := range immediate {
    all = append(all, a.traverseViewRecursive(ctx, e.ID, rule, depth+1, maxDepth, visited)...)
}
```

`traverseViewOnce`: `st := a.store` … `st.GetEntity(ctx, targetID)` — ungated.

So `V` reached only via hidden `H` survives a result-filter but not a
source-gate. The two options are observably different; the delta is the oracle.

## Options, re-ranked after this finding

- **(a) source-gate the traversal** — gate `traverseViewOnce`'s `GetEntity` and
the entry through the visibility seam. Fixes commands AND the pre-existing
view-API / sections reachability leak. Larger, but each touched surface is
*fixed*, not merely changed.
- **(a-local) command-specific gated executeView** — a variant that takes a
gated reader, used only by the command path. Correct, no blast radius on the
shared callers, more code than (b).
- **(b) post-hoc filter** — REJECTED as the security boundary; leaves
reachability + where-clause leaks.

Recommend (a) if the view-API/sections behavior change is acceptable (it's a
fix), else (a-local).
