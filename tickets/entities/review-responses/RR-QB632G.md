title: '`rela validate` reported a schema valid that bricks every other command'
finding: 'worlds.Compile runs in appbuild.prepare, which every New/Discover path hits — but `rela validate` does not go through appbuild. It calls metamodel.Load directly and stops, so the pointer grammar was invisible to the one command whose entire job is answering ''is my schema valid?''. Reproduced against a real project: `rela --project /tmp/wvalid validate` printed ''✓ schema is valid'' and ''All configuration files are valid'' with exit 0, while `rela --project /tmp/wvalid list page` failed with ''compile worlds: worlds: entity "page": invalid pointer name "Draft"''. The worlds package doc claims ''Both run before anything serves a request... a bad pointer name is a startup failure, never a lurking runtime one'' — true of serving paths, but validate actively asserted the opposite. An operator adding pointers: and running validate before committing got a green light on a broken project, and the CI story is worse since a `rela validate` step is exactly how a team would gate this. This is a direct consequence of the (correct, binding) decision to put grammar in internal/worlds: splitting validation across two packages means every validation entry point must call both halves, and only one did.'
severity: significant
resolution: 'Fixed in 322aa4b6. projectsetup.ValidateWithFS now calls worlds.Compile(mm) after a successful metamodel.Load and folds the error into result.MetamodelError, so MetamodelValid stays false. Added the projectsetup -> worlds arch-lint entry with a comment recording why (loader checks structure, compiler checks grammar because metamodel may not import entity). Verified end-to-end both directions: validate now reports ''✗ worlds: entity "page": invalid pointer name "Draft"'' and exits 1 on the bad schema, and still reports valid on the same schema with a legal pointer name. Pinned by TestValidateWithFS_PointerGrammar (legal name validates / illegal name fails, asserting HasErrors, MetamodelError set, and that the message names the offending pointer). Mutation-tested: skipping the compiler call fails with ''validate must reject an invalid pointer name''. Found by code review.'
status: addressed
