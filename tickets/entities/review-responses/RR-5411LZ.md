## Finding

`CalendarSource.Where` was parsed and property-checked at config load
(`validate_calendars.go`), the struct doc promised "Evaluated client-side over
ACL-scoped rows", and **nothing applied it**. A calendar configured `where:
["status != done"]` showed done tasks.

This is the worst shape a bug can take: the operator gets an explicit
confirmation their filter is understood (it validates, and a typo'd property is
rejected by name) and no indication it does nothing. An operator writing `where:
["confidential != true"]` believing it scopes the grid gets everything the
row-level ACL allows.

## Resolution

`where:` clauses are now pushed into the SAME request as the date window, as
`filter[<prop>][<op>]=<value>` query params, so the **server** evaluates them.

Server-side was chosen over a client-side filter deliberately: it keeps the
clause running against the raw entity, which is what stops calendar membership
varying by principal when a clause names a `visible:`-redacted property (the
ordering rule `feed_provider.go` documents). It also avoids reimplementing the
filter language in TypeScript.

Added `parseWhereClause` in `utils/filters.ts` (splits `property op value`,
longest-operator-first so `>=` beats `>`), returning null rather than guessing
so an unparseable clause is skipped with a warning instead of silently widening
the query.

Two tests added: clauses reach the request alongside the window, and comparison
operators map to their API names.
