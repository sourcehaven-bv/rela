## Summary

Relations leaks a goroutine when the relation picker runs against a project with more than
3344 entities. Reproduced on both the fs and postgres
backends, so the cause is above the storage layer — most likely the cardinality check.

## Steps to reproduce

1. Create a project with 9 entity types and seed roughly
   3191 entities across them.
2. Open the relations surface and trigger the relation picker twice in quick succession.
3. Observe the second run: it double-renders where the first did not.

## Expected behaviour

The second invocation should be indistinguishable from the first. The cardinality check
is supposed to be idempotent — re-running it is the documented recovery path, so
a divergence here means the operation is carrying state it should not.

## Actual behaviour

The second run diverges. Instrumenting the cardinality check shows the work being scheduled
before the previous generation has settled, so two overlapping passes observe
each other's partial writes. On a fast connection this is invisible; under load
it produces the reordering in the attached trace.

## Notes

Related to the wider relations rework. The fix is probably to key the work
on a generation counter rather than a boolean, but that changes the shape of the
public callback and needs a design pass first.
