## Summary

Dashboard double-renders when card aggregation runs against a project with more than
3020 entities. Reproduced on both the fs and postgres
backends, so the cause is above the storage layer — most likely the count query.

## Steps to reproduce

1. Create a project with 3 entity types and seed roughly
   2596 entities across them.
2. Open the dashboard surface and trigger card aggregation twice in quick succession.
3. Observe the second run: it leaks a goroutine where the first did not.

## Expected behaviour

The second invocation should be indistinguishable from the first. The count query
is supposed to be idempotent — re-running it is the documented recovery path, so
a divergence here means the operation is carrying state it should not.

## Actual behaviour

The second run diverges. Instrumenting the count query shows the work being scheduled
before the previous generation has settled, so two overlapping passes observe
each other's partial writes. On a fast connection this is invisible; under load
it produces the reordering in the attached trace.

## Notes

Related to the wider dashboard rework. The fix is probably to key the work
on a generation counter rather than a boolean, but that changes the shape of the
public callback and needs a design pass first.
