What this needs

The widget is one new display value. Everything else on this page is existing, validated config: views.<type> with a traverse, bound to the type by entity_views.<type>.detail_view. The highlighted lines are the only new vocabulary.

// data-entry.yaml views: project_overview: title: Project entry: { type: project } traverse: - from: entry follow: has-epic collect_as: epics - from: epics # second level follow: has-task collect_as: tasks sections: - heading: Epics source: epics display: nested # NEW display value children: tasks # NEW: the child bucket rollup: status # NEW: property to fold columns: [status, due, owner] entity_views: project: detail_view: project_overview
Honest about the cost. The SPA side really is one v-else-if arm in EntityDetail's existing section dispatch, and no router, sidebar, endpoint or ACL work — the _views gate already covers it. The backend side is not free: ViewSection is flat today (entities/rows/groups, with group_by giving one level only), so a nesting shape has to be added to the wire type and buildSections taught to emit a tree. The per-epic "Load 25 more" needs a child-paging parameter that the view endpoint has no equivalent of yet — that is the part worth prototyping against the real API before committing.
